_v0.4 · 28 ส.ค. 2569 · **ผ่านการทดสอบกับ git remote จริงแล้ว** (ดู §13)_
_เปลี่ยนจาก v0.2 หลังได้คำตอบ 3 ข้อ: **workspace + git** · **ผู้ทำงานขนานคือ agent** · **private repo ใช้ได้**_

## 2. Preflight — สคริปต์เดียวที่ agent ต้องรันก่อนแตะแอป

```bash
./tools/preflight.sh <agent-id> <task-id> <app-id> "<objects,csv>"
```

**exit ≠ 0 → หยุดและรายงานผู้ใช้ ห้ามยิงคำสั่งใด ๆ ใส่แอป**

| # | ขั้น | พฤติกรรมจริง (ทดสอบแล้ว) |
|---|---|---|
| 1 | commit WIP ที่ค้างอัตโนมัติ แล้ว `git pull --rebase` | มีงานค้างใน working tree **ไม่ทำให้ล้ม** · pull ไม่ได้ (remote ล่ม) → exit 1 และ tree สะอาด |
| 2 | อ่าน `shared/claims/*.log` หา CLAIM ที่ยังไม่มี RELEASE/HANDOFF/EXPIRED | — |
| 3 | ปลด CLAIM ที่เกิน `TTL_HOURS` (ตั้งต้น 8) → เขียน `EXPIRED` ลง log **ของตัวเอง** | แก้เคส agent ตายกลางคันแล้วบล็อกคนอื่นถาวร |
| 4 | ตรวจชน: app เดียวกัน + objects ทับกัน (รองรับ prefix `ac_voucher*`) | ชน → exit 1 พร้อมบอกว่า agent ไหนถือ task อะไรตั้งแต่เมื่อไร |
| 5 | ถ้ามี `handoff/<task-id>.md` → พิมพ์หัวข้อ "ยิงไปแล้ว" ออกมา | ไม่ล้ม แต่บังคับให้ agent เห็น |
| 6 | เขียน `CLAIM` ลง `shared/claims/<agent>.log` → commit → **push** | push ไม่ผ่าน = มีคน claim ก่อน → reset แล้ววนกลับข้อ 1 (สูงสุด 3 ครั้ง) |

**การชิงสิทธิ์ตัดสินที่ git remote ไม่ใช่ที่ความสุจริต** — agent สองตัวคุยกันไม่ได้ ⇒ **ใคร push CLAIM ขึ้นก่อนคือผู้ถือ** อีกตัว push ไม่ผ่าน วนตรวจใหม่ แล้วเห็นใบจองของคู่แข่ง จึงหยุดเอง

> ⚠️ **เป็นการจองเชิงมารยาท ไม่ใช่ล็อกจริง** — ไม่มีอะไรตรวจว่า agent ประกาศ `objects` ตรงกับที่แตะจริง และเซิร์ฟเวอร์ไม่บังคับให้ ⇒ ประกาศให้ครบเสมอ (คำเตือนนี้หายไปใน v0.3 — เอากลับ)

## 3. Postflight — จบ Task

`tools/postflight.sh <task-id> --release|--handoff`

| | `--release` | `--handoff` |
|---|---|---|
| ตรวจ | ZZTEST records เคลียร์แล้ว (ถามผู้ใช้ยืนยันถ้าตรวจอัตโนมัติไม่ได้) | ต้องมี `handoff/<task-id>.md` และหัวข้อ "ยิงไปแล้วบนเซิร์ฟเวอร์" **ไม่ว่าง** |
| เขียน log | `RELEASE` | `HANDOFF → handoff/<task-id>.md` |
| commit | รูปแบบ §4 | รูปแบบ §4 |
| ปิดงาน | ย้าย `handoff/<task-id>.md` → `handoff/.done/` | — |

**`git revert` ย้อนเอกสารได้ แต่ย้อนแอปไม่ได้** ⇒ หัวข้อ "ยิงไปแล้วบนเซิร์ฟเวอร์" คือเหตุผลที่ handoff มีอยู่ ถ้าไม่ได้แตะอะไรให้เขียน "ไม่มี" ชัด ๆ

เทมเพลต `handoff/<task-id>.md` — 4 หัวข้อ ห้ามตัดออก:
```markdown
## ยิงไปแล้วบนเซิร์ฟเวอร์ (ย้อนอัตโนมัติไม่ได้)
## ทำถึงไหน (เทียบ DoD)
## ที่ตั้งใจจะทำต่อ
## ระเบิดที่ฝังไว้ (ZZTEST ค้าง / index / ของกึ่งสร้าง)
```

## 4. commit — ตัวตนและรูปแบบ

**หนึ่ง clone ต่อหนึ่งสายงาน** (`~/work/nocoly-hr`, `~/work/nocoly-ac`) ตั้ง identity แยก:

```bash
git config user.name  "agent-hr"      # หรือ agent-ac / agent-api-lab
git config user.email "agent-hr@tilsna.local"
```

ได้สามอย่างพร้อมกัน: `blame` บอกได้ว่าสายไหนเขียน · ไฟล์ชนกันน้อยลงเพราะคนละ working tree · การชนถูกตัดสินที่ remote ตาม §2

```
docs(hr): D-17 คลี่คลาย — defaultValue ไม่ถูกใช้เมื่อ create_record ผ่าน MCP

Task: HR/D-17
App: deca7391
Objects: hr_leave_request, hr_ot_request
Evidence: V 2026-08-28 (Workflow History = Done, _updatedBy=user-workflow)
```

⚠️ `git blame` ตอบ "ข้ออ้างนี้เก่าแค่ไหน" **ไม่ได้** สำหรับเนื้อหาที่มีก่อน migrate — ทุกบรรทัดจะเป็นวันที่ย้ายเหมือนกันหมด ⇒ **ป้าย `[V] วันที่` ในเนื้อความยังจำเป็น**

## 5. `shared/claims/<agent>.log` — หนึ่งไฟล์ต่อหนึ่ง agent

> **v0.3 ออกแบบผิด และพิสูจน์แล้วว่าผิด** — ใช้ log ไฟล์เดียวร่วมกัน แล้วอ้างว่า "ต่อท้ายไม่ชน conflict"
> ความจริง: git รวมการต่อท้ายได้เฉพาะเมื่ออยู่ **คนละบริเวณ** ของไฟล์ · CLAIM สองใบต่อท้ายจุดเดียวกัน = conflict เหมือนแก้บรรทัดเดิม
> ทดสอบจริง: `B pull --rebase` → `CONFLICT: UU log.md` **ในสถานการณ์ที่กลไกนี้มีไว้แก้พอดี**

```
shared/claims/agent-hr.log
shared/claims/agent-ac.log
```

```
CLAIM   2026-08-28T09:00Z deca7391 HR/P5-6 hr_salary_structure,hr_payslip*
RELEASE 2026-08-28T16:40Z HR/P5-6
HANDOFF 2026-08-29T11:05Z AC/P8.6 handoff/AC-P8.6.md
EXPIRED 2026-08-29T12:00Z HR/ZOMBIE by=agent-ac was=agent-hr
```

- **ต่อท้ายเฉพาะไฟล์ของตัวเอง ห้ามแตะไฟล์ของ agent อื่น** (แม้แต่ตอนเขียน `EXPIRED` — ให้เขียนลงไฟล์ตัวเองว่าไปปลดของใคร)
- สถานะรวม = อ่านทุกไฟล์แล้วหักลบ CLAIM ที่มี closer แล้ว — **ต้องคำนวณสองรอบ ไม่ใช่รอบเดียว** เพราะลำดับการอ่านไฟล์ตามตัวอักษรทำให้ closer มาก่อน CLAIM ได้ (บั๊กจริงที่ชุดทดสอบจับได้)
- เกิน 500 บรรทัด → ตัดครึ่งบนไป `shared/claims/.archive/`

## 6. `ENV.md` — ค่าคงที่ระดับ repo

```yaml
docs_vcs: git
workspace_mode: cowork        # งานทั้งหมดทำใน workspace ไม่ใช่แชท
commit_by: agent              # ⚠ ทดสอบ 1 ครั้งแล้วบันทึกผลที่นี่
cli_available: unknown        # yes | no | unknown — มี hap ติดตั้ง+ล็อกอิน+เป็น admin ไหม
apps:
  deca7391-1761-424b-9af3-c8d043004ad3: ERP - TILSNA   # ใช้ร่วม tilsna-hr + tilsna-accounting
  23ce02b5-ef67-4f9e-b4f2-fc8d8818734c: API-Lab
```

`cli_available: unknown` → **ห้ามเขียน Surface = CLI ลง Build Spec** ให้ใช้ Browser · spec ที่สั่งไปยังพื้นผิวที่เข้าไม่ถึง แย่กว่าสั่งไป Browser

## 7. สำรองแอป — ทำได้เลยวันนี้ ไม่ต้องรอข้ออื่น

**สิ่งเดียวในระบบทั้งหมดที่สร้างใหม่ไม่ได้คือคอนฟิกแอปบนเซิร์ฟเวอร์** เอกสารเขียนใหม่ได้ แต่ worksheet ที่ถูกลบไม่ได้

```
hap app backup <appId>        # ก่อนงานที่แตะโครงสร้างเป็นชุด
hap app exports <appId>       # ดูรายการที่มี
hap app backup-logs <appId>   # ตรวจว่า backup สำเร็จจริง
hap app logs <appId>          # operation log ระดับแอป
```

ผูกเข้า `preflight.sh` เป็นขั้นที่ 0 เมื่อ Task ระบุว่าแตะโครงสร้าง · **ต้องยืนยันด้วย `backup-logs` ว่าสำเร็จจริง อย่าเชื่อว่าคำสั่งผ่าน = สำรองแล้ว**

## 8. สุขอนามัย private repo (ยังต้องมีแม้ private)

```
.hap-cli/            # profile / token — ห้ามขึ้นเด็ดขาด
*.ids.json
**/export-*.csv      # ข้อมูลจริงที่ export ออกมา
snapshots/**/*.json  # จนกว่าจะพิสูจน์ว่าไม่มีข้อมูล record ปน (03 §5)
```

เอกสารมีคำว่าเงินเดือน/ค่าจ้าง/บัญชีธนาคารกระจายใน 10 ไฟล์ ⇒ private repo แก้เรื่องคนนอก แต่ **ไม่แก้เรื่อง token หลุดหรือข้อมูลจริงถูก commit** ซึ่ง `.gitignore` ต้องกัน

## 9. Claude Project — ตัดสินใจครั้งเดียว

| ถ้า | ทำ |
|---|---|
| งานทั้งหมดย้ายเข้า workspace | **ลบ `PROJECT-SYNC.md` และเลิกอัปเข้า Project** — repo คือแหล่งเดียว |
| ยังใช้ Project สำหรับถาม/ปรึกษาคู่ขนาน | ให้ Project เป็น **สำเนาอ่านอย่างเดียว** อัปจาก `main` โดยขั้นตอนอัตโนมัติ ไม่ใช่คนอัปมือ และห้ามแก้ไฟล์ในนั้น |

ที่ห้ามคือ **แก้สองที่** — เพราะจะไม่มีทางรู้ว่าอันไหนใหม่กว่า

## 11. เกณฑ์เลิก — ต้องมี ไม่งั้นจะเสื่อมเป็นพิธีกรรม

ตรวจที่ **3 สัปดาห์**: นับ Task ที่มี CLAIM ใน log เทียบกับ Task ทั้งหมดใน Roadmap

| ผล | ทำ |
|---|---|
| ≥ 80% | ใช้ต่อ |
| 50–80% | หาสาเหตุว่าขั้นไหนถูกข้าม แล้วลดขั้นนั้น |
| < 50% | **ยกเลิก §2–§3** กลับไปใช้การเรียงคิว (ไม่ทำสองสายบน `deca7391` พร้อมกัน) ซึ่งแก้ปัญหาเดียวกันด้วยกลไกศูนย์ชิ้น |

ระบบที่ไม่มีตัววัดและไม่มีสวิตช์ปิด จะสร้างความมั่นใจปลอม — "เรามีไฟล์จองอยู่นะ" ทั้งที่ไม่มีใครเขียน ซึ่งแย่กว่าไม่มีเลย

## 12. คำถามที่ระบบนี้ต้องตอบได้

| คำถาม | ตอบด้วย |
|---|---|
| Task นี้แก้อะไร สายไหนทำ หลักฐานอะไร | `git log --grep "Task: HR/D-17"` |
| ตอนนี้สายไหนถืออะไรอยู่ | CLAIM ที่ยังไม่มีคู่ปิด (30 บรรทัดท้าย) |
| รับงานต่อต้องระวังอะไร | `handoff/<task-id>.md` |
| กับดัก `kind:"record"` เคยถูกแก้กลับไหม | `git log -S 'kind:"record"' -p` |
| ข้ออ้างนี้เก่าแค่ไหน | ป้าย `[V] วันที่` ในเนื้อความ **ไม่ใช่ blame** |
| แอปถูกสำรองล่าสุดเมื่อไร | `hap app backup-logs <appId>` |

ถ้าข้อไหนตอบไม่ได้ กลไกยังขาด — **อย่าเพิ่มกลไกที่ไม่มีคำถามรองรับ**

## 13. ผลการทดสอบ (28 ส.ค. 2569)

ตั้ง `git daemon` บน `git://127.0.0.1/repo.git` + `pre-receive` hook หน่วง 0–0.3 วิ แบบสุ่มเพื่อถ่างช่องแข่ง แล้ว clone แยกต่อ agent

| ชุด | ผล |
|---|---|
| ฟังก์ชัน 11 เคส (จอง · ปล่อย · handoff บังคับกรอก · TTL · WIP ค้าง) | **PASS 11 / FAIL 0** |
| 2 agent × 20 รอบ แข่งขนานจริง (`&` + `wait`) | ได้สิทธิ์ตัวเดียวทุกรอบ · **ได้ทั้งคู่ = 0** · tree สกปรก = 0 · conflict ค้าง = 0 |
| 3 agent × 10 รอบ | ได้สิทธิ์ตัวเดียวทุกรอบ |
| integrity หลัง 20 รอบ | CLAIM 20 / RELEASE 20 · ไม่มีใบค้าง ไม่มี task ซ้ำ |
| remote ล่มกลางคัน | exit 1 · working tree สะอาด ไม่มี index ค้าง |

**บั๊ก 2 ตัวที่การอ่านโค้ดไม่เห็น แต่การยิงจริงจับได้**

1. `EXPIRED` ถูกเขียนข้ามไปยัง log ของ agent อื่น — เป็นรอยเดิมของปัญหา conflict ที่กลับมาอีกทาง
2. การคำนวณสถานะแบบรอบเดียวขึ้นกับลำดับตัวอักษรของชื่อไฟล์ — zombie claim รอดมาบล็อกงานเมื่อชื่อ agent เรียงในทางหนึ่ง (ทำงานถูกเมื่อ `agent-hr` ปลดของ `agent-ac` แต่พังในทิศตรงข้าม)

**ยังไม่ได้ทดสอบ — ต้องรันบน private repo จริงก่อนเชื่อทั้งหมด**

- auth (SSH key / PAT หมดอายุกลางคัน)
- **branch protection** — ถ้าเปิด require-PR ไว้ `push` ตรงจะถูกปฏิเสธและกลไกทั้งหมดพัง ⇒ ต้องให้ push ตรงได้ หรือแยก branch สำหรับ claims
- latency ข้ามอินเทอร์เน็ตจริง (ยาวกว่า 0.3 วิมาก — เพิ่ม retry แต่ไม่ควรเปลี่ยนผลเชิงตรรกะ)
- `postflight --release` ยังไม่ได้ตรวจ ZZTEST ค้างอัตโนมัติ

วิธีทดสอบซ้ำ: `tools/run-tests.sh` (ฟังก์ชัน) และสคริปต์แข่งขนานใน §13 — **กลไกแบบนี้พิสูจน์ด้วยการอ่านไม่ได้ ต้องยิงเท่านั้น**
