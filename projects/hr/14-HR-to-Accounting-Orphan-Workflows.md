# ส่งต่อฝ่ายบัญชี — พบ orphan workflow และฉบับซ้ำในโมดูลบัญชี 12 ตัว

**จาก:** build agent โมดูล HR · TILSNA ERP
**วันที่:** 28 สิงหาคม 2569
**บริบท:** ระหว่างล้าง orphan workflow ฝั่ง HR (ตกค้างจากการ revert งาน D-8) ได้สแกน workflow **ทั้งแอป** เพื่อยืนยันว่าไม่มีใครอ้างถึงตัวที่จะลบ — ระหว่างนั้นพบของฝั่งบัญชีที่เข้าข่ายเดียวกัน จึงส่งเรื่องมาให้พิจารณา

## ✅ สถานะล่าสุด — 28 สิงหาคม 2569 (ตรวจซ้ำหลังฝ่ายบัญชีเริ่มเคลียร์พร้อมกัน)

ฝ่ายบัญชีแจ้งว่ากำลังเคลียร์อยู่พร้อมกัน — ตรวจสถานะจริงด้วย `hap workflow get <id>` (ฟิลด์ `deleted`) แล้วได้ผลดังนี้:

- **เคลียร์แล้ว 9/12** — inner ไม่มี parent ทั้ง 7 ตัวในข้อ 1 (รวม 4 ตัวที่เคย `enabled:true`) · `WF-AC-02` ฉบับซ้ำ · `ปิดปีและยกยอด` (`6a90ef43…`) — ทั้งหมด `deleted:true, enabled:false`
- **ยังเหลือ 3 ตัว** (ทั้งหมด `deleted:false`, ปิดใช้งานอยู่ ไม่เป็นอันตรายเฉพาะหน้า): `ปิดงวด` `6a903eb8fdab77a41c5697ca` · `ปิดปีและยกยอด` `6a90f50e0e97bf440de723d7` · `กลับรายการ` `6a8fb9eae6605c4b13dc846d`
- ✅ **ตรวจแล้ว workflow บัญชีที่ใช้งานจริงทั้ง 9 ตัวปลอดภัยครบ ไม่มีตัวไหนโดนลบพลาด** (WF-AC-01 + approval sub-flow · WF-AC-02 · WF-AC-09 · WF-AC-10 + inner ที่ใช้จริง 3 ตัว · WF-AC-11)
- ✅ **ฝั่ง HR ก็ไม่ถูกกระทบ** — WF-HR-01…06 พร้อม inner ครบ 12 process โครงสร้างสมบูรณ์

> 🔴 **สำคัญ — วิธีตรวจที่ถูกต้อง:** `hap workflow structure <id>` **คืนโครงสร้างเต็มแม้ process ถูกลบไปแล้ว** ใช้ยืนยันการมีอยู่ไม่ได้เลย · และ `hap workflow list` ก็ไม่ครบ ⇒ **ต้องใช้ `hap workflow get <id>` ดูฟิลด์ `deleted` เท่านั้น** · อนึ่ง `delete_process` เป็น **soft-delete** (ได้ `deleted:true, enabled:false` แต่ object ยังดึงด้วย id ได้) ไม่ใช่ลบถาวร

> 🔴 **HR ไม่ได้แตะ ไม่ได้ลบ และจะไม่ลบให้** — เป็น object ของโมดูลบัญชี และ 3 ตัวมีสถานะ `enabled:true` ซึ่งอาจยังถูกอ้างผ่านเส้นทางที่การสแกนของ HR ตรวจไม่พบ · ขอให้ฝ่ายบัญชียืนยันเองก่อนลบทุกตัว

## 3. ตรวจแล้วว่า **ไม่ใช่** ตัวซ้ำ (ห้ามลบ)

`6a8eaa76730d20c5b76071f3` "อนุมัติใบสำคัญ (WF-AC-01)" — ตอนแรกดูเหมือนซ้ำกับ `6a8eaa45e6605c4b13ccf49b` "WF-AC-01 อนุมัติใบสำคัญ" เพราะ **enabled ทั้งคู่** แต่ตรวจ trigger แล้วพบว่าเป็นคนละบทบาท: ตัวหลังมี `appType:9` และ `triggerId` ชี้กลับไปที่ตัวแรก = เป็น **approval sub-flow ที่ WF-AC-01 เรียกใช้** (ชื่อ trigger ในระบบคือ `发起审批`) ไม่ใช่ workflow ซ้ำ — เหมือนโครงสร้าง WF-HR-01/WF-HR-04 ของฝั่ง HR

## 4. ข้อควรระวังที่ HR เจอระหว่างทำงานนี้ (ฝ่ายบัญชีน่าจะใช้ได้ด้วย)

1. **`hap workflow list <app_id>` ให้ผลไม่คงที่และไม่ครบ** — เรียก 3 ครั้งได้ 50 / 37 / 36 รายการ · inner ของ WF-HR-05 ไม่ปรากฏในการเรียกครั้งแรกเลยทั้งที่มีอยู่จริงและถูกใช้งานอยู่ ⇒ **ห้ามใช้ผลจาก list สรุปว่า "ไม่มี" อะไร** ต้องยืนยันรายตัวด้วย `hap workflow structure <id>`
2. **คีย์ที่ใช้อ้าง inner process ต่างกันตามเครื่องมือ** — MCP `get_workflow_structure` ใช้ `config.process.processId` · hap CLI ใช้ `flowNodeMap.<nodeId>.subProcessId` · ส่วน approval sub-flow ผูกผ่าน `triggerId` ไม่ใช่ทั้งสองตัว ⇒ เวลาเขียน script หา orphan ให้ **grep แบบ full-text ทั้ง output** อย่าเจาะจงคีย์ (HR จับผิดคีย์รอบแรกแล้วได้ผลลวงว่า "ทุก inner เป็น orphan")
3. **สำรอง `workflow structure` ลงไฟล์ก่อนลบเสมอ** — `delete_process` ลบแล้วเรียกคืนไม่ได้
