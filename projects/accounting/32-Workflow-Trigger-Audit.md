# 32 · ไล่ตรวจ trigger ของ workflow ทั้งโมดูล AC · agent-ac · 7 ก.ย. 2569

> ใบจอง `AC/WF-TRIGGER-AUDIT` · เริ่มจาก AC-R-34 ที่พบโดยบังเอิญ แล้วขยายเป็นการไล่ตรวจทั้งโมดูล
> **ผลคือปัญหาไม่ได้อยู่ที่ workflow ตัวเดียว แต่เป็นรูปแบบเดียวกันทั้งชุด**

---

## 1. แผนที่ `triggerId` — ยืนยันแล้ว ไม่ใช่การเดา

`hap workflow get` คืน `triggerId` เป็นตัวเลข แต่**ไม่มีเอกสารบอกความหมาย** · ผมเดาครั้งแรกแล้วได้ผลที่ไร้เหตุผล
(workflow 11 ตัวถูกตีความว่า trigger = "ลบ" ซึ่งเป็นไปไม่ได้สำหรับ "อนุมัติใบสำคัญ")

จึงยืนยันด้วยการเทียบกับ MCP `get_workflow_structure` ที่คืนชื่อเชิงความหมาย

| `triggerId` | ความหมายจริง | หลักฐาน |
|---|---|---|
| `1` | **add** (สร้างระเบียน) | WF-AC-08 → MCP ตอบ `event: "add"` |
| `2` | **update** (ทุกฟิลด์) | WF-AC-21 / 30 / 33 — ผมสร้างเองด้วย `update` และ `assignFieldIds` ว่าง |
| `4` | **update เฉพาะฟิลด์ที่ระบุ** | WF-AC-32 → MCP ตอบ `event: "update"` + `triggerFields: [...]` · `assignFieldIds` มีค่า |
| `3` | น่าจะเป็น `add_or_update` | **ไม่มี workflow ตัวไหนในโมดูล AC ใช้เลย** |

> 🔑 **D-69** — `triggerId` ที่ CLI คืนมาไม่มีเอกสารกำกับ · ต้องยืนยันกับ MCP `get_workflow_structure` ซึ่งคืน `event` เป็นคำ (`add` / `update` / `delete` / `add_or_update`) ก่อนสรุปอะไรจากตัวเลข · **ตัวแยกที่ใช้ได้จริงคือ `assignFieldIds` ว่างหรือไม่** (ว่าง = ทุกฟิลด์ · มีค่า = เฉพาะฟิลด์นั้น)

### 🔴 ข้อสรุป

**ระบบอัตโนมัติทั้ง 14 ตัวที่ผูกกับตารางเอกสาร มองไม่เห็นการ "สร้างระเบียน" เลย**

| **WF-AC-24 กันใบแจ้งหนี้ซ้ำ** | 🔴 **ตัวกันเอกสารซ้ำที่ไม่ทำงานตอนสร้างเอกสาร = ไม่ได้กันอะไรเลย** — คีย์ใบซ้ำเข้ามาตรง ๆ ผ่านฉลุย |

**ลำดับที่ใช้ (ปลอดภัยกว่าลบก่อนสร้าง):** สร้างใหม่ → validate → **ปิดตัวเดิม (`--disable`)** → publish ตัวใหม่ → ทดสอบ → ลบตัวเดิมทิ้ง

### ผลทดสอบ — เคสที่เดิมพัง

สร้างใบเสร็จ `ZZTEST-RE-ADD-01` **พร้อมสถานะ "รับเงินแล้ว" ตั้งแต่แรก** (รับ 10,000 · ถูกหักภาษี 300)


## 4. ที่ยังไม่ได้แก้ — 13 ตัว

**ไม่แก้รวดเดียวโดยพลการ** เพราะแต่ละตัวต้องสร้าง process ใหม่ทั้งตัวแล้วลบตัวเก่า ซึ่งมีความเสี่ยงต่อระบบที่ใช้งานอยู่
เรียงตามความเสี่ยงที่แนะนำให้แก้ก่อน ⇒ **AC-R-43**

| ลำดับ | workflow | เหตุผล |
|---|---|---|
| 1 | **WF-AC-24 กันใบแจ้งหนี้ซ้ำ** | ตัวกันซ้ำที่ไม่ทำงานตอนสร้าง = ไม่ได้กันอะไร · ผลคือข้อมูลเสียแบบตรวจจับไม่ได้ |
| 2 | WF-AC-01 + WF-AC-02 | ใบสำคัญที่สร้างมาพร้อมสถานะอนุมัติจะไม่เข้า GL |
| 3 | WF-AC-31 · WF-AC-25 · WF-AC-26 | เอกสารไม่ออกใบสำคัญ |
| 4 | WF-AC-23 · WF-AC-30 | ภาษีไม่ถูกคำนวณ |
| 5 | WF-AC-09 · WF-AC-10 · WF-AC-11 · WF-AC-21 · WF-AC-33 | ผลกระทบจำกัดกว่า |

> ⚠️ **ก่อนแก้ตัวไหน ต้องดูก่อนว่ามันควรยิงตอนสร้างจริงไหม** — บาง workflow ออกแบบมาให้ยิงเฉพาะตอนเปลี่ยนสถานะโดยตั้งใจ การเปลี่ยนเป็น `add_or_update` แบบเหมารวมอาจทำให้ยิงตอนสร้างร่างซึ่งไม่ต้องการ · **ตัวที่ปลอดภัยคือตัวที่มี branch guard อยู่แล้ว** (เช่น WF-AC-32 ที่เช็ค "ยังไม่มีใบสำคัญ")

## 5. สูตรที่ใช้ได้ (ทำซ้ำได้กับอีก 13 ตัว)

```
1. get_workflow_structure ตัวเดิม → คัดลอกโครง node ทั้งหมดออกมา
2. create_process ด้วย trigger ใหม่ (add_or_update + triggerFields เดิม)
3. batch_create_process_nodes ทีละชุด — ⚠️ node ที่อยู่ใต้ branch ของ "ชุดก่อนหน้า"
   ต้องอ้าง prevNode ด้วย nodeId ของ path (อ่านจาก hap workflow get) ไม่ใช่ parentNode + alias
4. validate_process → ต้องได้ issueCount 0
5. ปิดตัวเดิม (hap workflow publish <id> --disable)
6. publish_process ตัวใหม่
7. ทดสอบเคสที่เดิมพัง + เคสเดิมที่เคยผ่าน + ตรวจว่าไม่ยิงซ้ำ
8. เก็บกวาดข้อมูลทดสอบตามลำดับ GL → รายการ → ใบสำคัญ → เอกสารต้นทาง
9. ลบ process เดิม
```

> 🔑 **D-70** — node ที่ต่อจาก branch **ต้องใช้ `prevNode` เป็น `nodeId` ของ path** เมื่อ branch ถูกสร้างในคำสั่งก่อนหน้า · ส่ง `parentNode` + alias ข้ามชุดจะได้ `INVALID_NODE: 分支后的节点必须接到 paths[].alias` · path มี nodeId ของตัวเองที่อ่านได้จาก `hap workflow get` (type 2)
