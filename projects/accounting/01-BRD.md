## 1. บทนำ

**1.1 วัตถุประสงค์เอกสาร** — กำหนดขอบเขต ความต้องการ และเกณฑ์ยอมรับของโมดูลบัญชีในโครงการ TILSNA ERP เพื่อให้ผู้บริหาร ผู้ตรวจรับ และทีมสร้างระบบเห็นตรงกันก่อนลงมือสร้างต่อบนแพลตฟอร์ม Nocoly

**1.2 ขอบเขตระบบโดยย่อ** — โมดูลบัญชีเป็น **แหล่งความจริงเดียวของข้อมูลการเงินขององค์กร**: รับหรือสร้างรายการทางธุรกิจ → คำนวณภาษีให้ถูกต้อง → แปลงเป็นรายการบัญชีคู่ (double entry) → ชำระเงิน → ออกงบการเงินและแบบยื่นภาษี

**1.3 ระดับรายละเอียด** — ระดับธุรกิจและ FR ระดับสูง · รายละเอียด implementation (worksheet, field, workflow node, ID) อยู่ใน Build Spec

**1.4 กรอบกฎหมาย ระเบียบ และมาตรฐานอ้างอิง**

| กรอบอ้างอิง | ผลต่อระบบ |
|---|---|
| ประมวลรัษฎากร — จุดความรับผิดภาษีมูลค่าเพิ่ม (tax point) และสิทธิ์เครดิตภาษีซื้อ | บังคับให้มีทะเบียนภาษีซื้อ–ขาย และบัญชีภาษีซื้อรอเรียกคืน (deferred input VAT) |
| ประมวลรัษฎากร — อัตราภาษีหัก ณ ที่จ่ายและแบบยื่น ภ.ง.ด.3 / 53 / 54 | บังคับให้มีตารางอัตราตามประเภทเงินได้ + ใบรับรองหัก ณ ที่จ่าย |
| แบบ ภ.พ.30 / ภ.พ.36 (ยื่นปกติและยื่นเพิ่มเติม) | บังคับให้มีตารางบันทึกการยื่น ไม่ใช่แค่รายงาน |
| พ.ร.บ.การบัญชี พ.ศ. 2543 — การเก็บรักษาเอกสารทางบัญชี | เก็บเอกสาร 5 ปี + ห้ามลบรายการที่ผ่านรายการแล้ว |
| มาตรฐานการบัญชีภาครัฐ / นโยบายบัญชีของกรมบัญชีกลาง | ผังบัญชี เกณฑ์คงค้าง และรูปแบบงบการเงิน |
| พ.ร.บ.คุ้มครองข้อมูลส่วนบุคคล พ.ศ. 2562 (PDPA) | ปกปิดเลขประจำตัวผู้เสียภาษีบุคคลธรรมดาและเลขบัญชีธนาคารจากผู้ที่ไม่มีหน้าที่ |
| ระบบ GFMIS / e-GP | ต้องส่งออกรหัสบัญชีมาตรฐานภาครัฐได้ |

**1.5 ผู้จัดทำและผู้เกี่ยวข้อง** — VBix Innovation Co., Ltd. (ผู้ออกแบบและสร้าง) · องค์กรเจ้าของระบบ TILSNA (ผู้ใช้และผู้ตรวจรับ)

## 2. ภูมิหลังและปัญหา (Pain Points)

โมดูลบัญชีรุ่น 1.0 วางระบบควบคุมได้ถูกต้อง (บัญชีคู่ ผังบัญชี งวดบัญชี การผ่านรายการ) แต่ **ชั้นรายการธุรกรรมบางเกินไป** — บันทึกรายการบัญชีได้ แต่ตั้งต้นเอกสารทางธุรกิจไม่ได้ คิดภาษีระดับบรรทัดไม่ได้ ตัดชำระไม่ได้ และไม่มีที่เก็บว่ายื่นภาษีอะไรไปแล้วบ้าง เวอร์ชัน 2.0 ปิดช่องว่างเหล่านี้

| # | ปัญหา | ผลกระทบ |
|---|---|---|
| P-1 | ภาษีมูลค่าเพิ่มถูกเก็บเป็นยอดรวมระดับหัวเอกสาร | เอกสารจริงมีหลายอัตราปนกันในใบเดียว (ปกติ / ศูนย์ / ยกเว้น) ทำ ภ.พ.30 ให้ถูกต้องไม่ได้ |
| P-2 | ไม่มีการควบคุมจุดความรับผิดทางภาษี (tax point) | เครดิตภาษีซื้อถูกใช้ผิดงวดหรือสูญไป เพราะภาษีซื้อเรียกคืนตามวันที่ใบกำกับ ไม่ใช่วันที่ตั้งค้างจ่าย |
| P-3 | ไม่มีที่เก็บ "ยื่นแบบอะไร เมื่อไร จำนวนเท่าไร" | ตอบผู้สอบบัญชีไม่ได้ · ยื่นเพิ่มเติมแล้วตามรอยไม่ได้ |
| P-4 | ไม่มีใบสำคัญจ่ายและกระบวนการเตรียมจ่าย | เงินออกก่อนมีเอกสารรองรับ · ใบรับรองหัก ณ ที่จ่ายไม่มีเอกสารอ้างอิง |
| P-5 | ไม่มีระบบใดในโครงการออกใบแจ้งหนี้ / ใบกำกับภาษี / ใบเสร็จ | ถ้าโมดูลบัญชีไม่ทำ ไม่มีใครทำ (ดูข้อสมมติ A-09) |
| P-6 | ค่าเสื่อมราคารับตัวเลขสำเร็จจากโมดูลสินทรัพย์ | อายุการใช้งาน มูลค่าซาก และวิธีคิดเป็นดุลพินิจทางบัญชี ต้องอยู่ในบัญชี |
| P-7 | รูปแบบเลขที่เอกสารถูกฝังในโค้ด | เปลี่ยนต้นปีงบประมาณทีต้องแก้ระบบทุกครั้ง |
| P-8 | เอกสารกระดาษเข้ามาปริมาณใกล้เคียงกับที่มาจากระบบจัดซื้อ | ไม่มีเส้นทางรับเอกสารด้วยการสแกนอย่างเป็นทางการ |
| P-9 | รองรับหลายสกุลเงินเพียงกฎเดียว ("ต้องมีอัตราแลกเปลี่ยน") | ยอดคงเหลือเงินบาทไม่ถูกต้อง · ปรับปรุงอัตราปลายงวดไม่ได้ |

## 3. วัตถุประสงค์ทางธุรกิจ (Business Objectives)

- **BO-1** ให้โมดูลบัญชีเป็นแหล่งความจริงเดียวของข้อมูลการเงิน — ทุกรายการเข้าสู่บัญชีแยกประเภทผ่านกฎการผ่านรายการชุดเดียวกัน ไม่ว่าจะเข้ามาทางใด
- **BO-2** ผลิตแบบยื่นภาษีตามกฎหมายไทยได้ครบและกระทบยอดกับบัญชีแยกประเภทได้ (ภ.พ.30, ภ.พ.36, ภ.ง.ด.3, ภ.ง.ด.53)
- **BO-3** ควบคุมการอนุมัติตามวงเงินและแยกหน้าที่ (Segregation of Duties) โดยตรวจสอบย้อนกลับได้ทุกการเปลี่ยนแปลง
- **BO-4** ลดงานคีย์ซ้ำ — รับรายการอัตโนมัติจากจัดซื้อ เงินเดือน และการสแกนเอกสาร
- **BO-5** ปิดงวดบัญชีได้ตรงเวลาโดยมีรายการตรวจสอบที่บังคับใช้จริง ไม่ใช่แค่คำแนะนำ
- **BO-6** ทำงานสองภาษา (ไทย/อังกฤษ) ทั้งข้อมูลหลักและงบการเงิน
- **BO-7** ทุก business logic อยู่บนแพลตฟอร์ม Nocoly — ไม่มีสคริปต์ภายนอกเป็นส่วนประกอบของระบบที่ส่งมอบ

## 4. ขอบเขต

### 4.1 อยู่ในขอบเขต (In scope)

ผังบัญชี มิติทางบัญชี และงวดบัญชี · การบันทึกใบสำคัญ สมุดรายวัน และบัญชีแยกประเภท · ค่าใช้จ่ายและเจ้าหนี้ รวมการรับเอกสารด้วยการสแกน · การเตรียมจ่าย ใบสำคัญจ่าย และการบันทึกตัดชำระ · ~~ลูกหนี้และห่วงโซ่เอกสารขาย (ใบแจ้งหนี้ ใบกำกับภาษี ใบเสร็จ ใบลดหนี้ ใบเพิ่มหนี้)~~ [ย้ายออกนอกขอบเขต 28 ส.ค. 2569 — ดู A-09 §11] · ภาษีมูลค่าเพิ่มพร้อมการควบคุม tax point และการบริหารเครดิตภาษีซื้อ · ภาษีหัก ณ ที่จ่าย ใบรับรอง และการเตรียมแบบยื่น · บัญชีสินทรัพย์ถาวรและตารางค่าเสื่อมราคา · การกระทบยอดธนาคาร · การปิดงวด ปิดบัญชีรายได้–ค่าใช้จ่าย และปิดปี · งบการเงิน แบบยื่นภาษี และรายงานทางบัญชี

### 4.2 นอกขอบเขต — เป็นของโมดูลอื่น

| หน้าที่ | โมดูลเจ้าของ | จุดเชื่อมกับบัญชี |
|---|---|---|
| จัดทำงบประมาณ โอนงบ และกันวงเงิน | Budget Management | บัญชีสอบถามวงเงินคงเหลือก่อนรับรู้หนี้สิน |
| การจ่ายเงินจริง — ไฟล์โอนเงิน พิมพ์เช็ค เงินสด บริหารเงินสด | Financial Management | บัญชีออกใบสำคัญจ่าย · การเงินจ่ายจริงแล้วส่งผลกลับ |
| ใบขอซื้อ ใบสั่งซื้อ สัญญา และการตรวจรับพัสดุ | Procurement & Contract | การตรวจรับกระตุ้นการรับรู้หนี้สิน |
| ทะเบียนสินทรัพย์ทางกายภาพ การครอบครอง ตรวจนับ | Inventory & Asset | ใช้รหัสสินทรัพย์ร่วมกัน · บัญชีถือ "สมุดบัญชีสินทรัพย์" |

## 6. กระบวนการเป้าหมาย (To-Be)

**6.1 สายรายจ่าย** — เอกสารเข้าระบบ 4 ทาง (จัดซื้อตรวจรับ / เงินเดือน / สแกนเอกสาร / คีย์เอง) → ตั้งหนี้พร้อมคิด VAT และหัก ณ ที่จ่ายระดับบรรทัด → อนุมัติตามวงเงิน → ผ่านรายการเข้าบัญชีแยกประเภท → ตั้งคำขอเบิก → ออกใบสำคัญจ่าย → การเงินจ่ายจริง → บันทึกตัดชำระ → ออกใบรับรองหัก ณ ที่จ่าย → รวมเข้าแบบยื่น

**6.2 สายรายรับ** — ใบแจ้งหนี้ → ใบกำกับภาษี → ใบเสร็จรับเงิน (พร้อมใบลดหนี้/เพิ่มหนี้เมื่อมีการปรับปรุง) → รับรู้รายได้และภาษีขาย → รวมเข้า ภ.พ.30

**6.3 สายควบคุม** — ทุกใบสำคัญต้องเดบิตเท่าเครดิตก่อนส่งอนุมัติ · ห้ามบันทึกในงวดที่ปิดแล้ว · ห้ามผู้จัดทำอนุมัติเอกสารของตนเอง · บัญชีแยกประเภทแก้ไม่ได้ (แก้ด้วยใบสำคัญกลับรายการเท่านั้น)

**6.4 สายปิดงวด** — รายการตรวจสอบปิดงวด → ปรับปรุงอัตราแลกเปลี่ยน → คิดค่าเสื่อมราคา → กระทบยอดธนาคาร → ปิดบัญชีรายได้–ค่าใช้จ่าย → ปิดงวด → ปิดปีและยกยอด

## 7. ความต้องการเชิงธุรกิจ (Business Requirements)

| รหัส | ความต้องการ | ความสำคัญ |
|---|---|---|
| BR-01 | ทุกรายการทางบัญชีต้องเกิดจากใบสำคัญที่เดบิตเท่ากับเครดิต และผ่านการอนุมัติก่อนเข้าบัญชีแยกประเภท | สูงสุด |
| BR-02 | บัญชีแยกประเภทต้องแก้ไขหรือลบไม่ได้ — การแก้ทำผ่านใบสำคัญกลับรายการเท่านั้น | สูงสุด |
| BR-03 | ห้ามบันทึกหรือผ่านรายการในงวดที่ปิดแล้ว · การเปิดงวดใหม่ต้องมีผู้มีอำนาจอนุมัติและบันทึกเหตุผล | สูงสุด |
| BR-04 | สายอนุมัติต้องเดินตามวงเงินและตารางมอบอำนาจ ซึ่งแก้ไขได้โดยไม่ต้องแก้ workflow | สูง |

| BR-21 | ต้องรับเอกสารด้วยการสแกน และห้ามส่งเอกสารที่ยังมีฟิลด์ความเชื่อมั่นต่ำที่ยังไม่ยืนยัน | กลาง (ขึ้นกับ A-12) |

## 8. ความต้องการเชิงหน้าที่ระดับสูง (Functional Requirements)

| รหัส | โมดูล | คำอธิบายระดับสูง |
|---|---|---|
| FR-01 | ตั้งค่าเอกสารและกฎอนุมัติ | สมุดรายวัน ประเภทเอกสาร กฎการออกเลขที่ กฎอนุมัติตามวงเงิน พฤติกรรมเอกสาร และกฎการผ่านรายการอัตโนมัติ ทั้งหมดเป็นข้อมูลตั้งค่า ไม่ใช่โค้ด |
| FR-02 | งวดบัญชี | ปีบัญชี งวด สถานะเปิด/ปิดชั่วคราว/ล็อกถาวร และสถานะงวดภาษีแยกจากงวดบัญชี |
| FR-03 | ผังบัญชีและมิติ | ผังบัญชีแบบลำดับชั้น พร้อมมิติหน่วยงาน แหล่งเงิน และโครงการ รวมข้อกำหนดว่าบัญชีใดบังคับมิติใด |
| FR-04 | คู่ค้าและบัญชีธนาคาร | ทะเบียนคู่ค้าพร้อมคุณลักษณะทางภาษี (เลขผู้เสียภาษี สำนักงานใหญ่/สาขา) และบัญชีธนาคารสำหรับจ่ายเงิน |
| FR-05 | ข้อมูลหลักด้านภาษีและสินค้า | สินค้า/บริการ อัตรา VAT อัตราและประเภทเงินได้หัก ณ ที่จ่าย สกุลเงิน อัตราแลกเปลี่ยน ประเภทสินทรัพย์ และช่องทางจ่ายเงิน — ทุกตัวมีวันที่มีผลบังคับ |
| FR-06 | ใบสำคัญและบัญชีแยกประเภท | บันทึกใบสำคัญพร้อมบรรทัดเดบิต–เครดิต ตรวจดุล อนุมัติตามวงเงิน ผ่านรายการแบบทำซ้ำไม่ได้ และกลับรายการ |
| FR-07 | ค่าใช้จ่ายและเจ้าหนี้ | เอกสารตั้งหนี้พร้อมบรรทัดค่าใช้จ่ายที่คิด VAT และหัก ณ ที่จ่ายรายบรรทัด พร้อมยอดคงค้าง |
| FR-08 | วงจรการจ่ายเงิน | คำขอเบิก → ใบสำคัญจ่ายหลายคู่ค้าหลายเอกสาร → บันทึกตัดชำระรายคู่ค้า → ส่งต่อให้การเงิน |
| FR-09 | ภาษีหัก ณ ที่จ่าย | ออกใบรับรองตามจังหวะที่ตั้งค่า (ตอนตั้งหนี้หรือตอนจ่าย) พิมพ์ตามแบบราชการ และรวมเข้าแบบยื่น |
| FR-10 | ทะเบียนเอกสารภาษีมูลค่าเพิ่ม | ทะเบียนภาษีซื้อ–ขาย พร้อม tax point สถานะการใช้เครดิต และการโอนภาษีซื้อรอเรียกคืน |
| FR-11 | การยื่นแบบภาษี | เตรียม อนุมัติ และบันทึกการยื่น ภ.พ.30 / ภ.พ.36 / ภ.ง.ด.3 / ภ.ง.ด.53 ทั้งยื่นปกติและเพิ่มเติม พร้อมไฟล์นำส่ง |
| FR-12 | ลูกหนี้และห่วงโซ่เอกสารขาย | ใบแจ้งหนี้ → ใบกำกับภาษี → ใบเสร็จ พร้อมใบลดหนี้และใบเพิ่มหนี้ที่อ้างอิงต้นฉบับเสมอ — ❌ **ย้ายออกนอกขอบเขตถาวร 28 ส.ค. 2569 (ยืนยัน A-09 §11) — ห้ามสร้าง จะอยู่ในโมดูลขายแยกต่างหากในอนาคต** |
| FR-13 | บัญชีสินทรัพย์ถาวร | สมุดบัญชีสินทรัพย์ ตารางค่าเสื่อมราคารายงวด การผ่านรายการค่าเสื่อม และการตัดจำหน่ายพร้อมกำไร/ขาดทุน |
| FR-14 | กระทบยอดธนาคาร | จับคู่รายการตามบัญชีกับรายการเดินบัญชีธนาคาร และสรุปผลต่าง |
| FR-15 | ปิดงวดและปิดปี | รายการตรวจสอบปิดงวด ปิดบัญชีรายได้–ค่าใช้จ่ายเข้ากำไรสะสม ยกยอดปีใหม่ และยอดยกมาตอนเริ่มใช้ระบบ |
| FR-16 | รายงานและแดชบอร์ด | งบทดลอง งบแสดงฐานะการเงิน งบผลการดำเนินงาน รายงานภาษีซื้อ–ขาย อายุหนี้ ต้นทุนโครงการ และแดชบอร์ดผู้บริหาร |
| FR-17 | การเชื่อมต่อระบบ | รับรายการจากจัดซื้อและเงินเดือน · ส่งใบสำคัญจ่ายให้การเงิน · สอบถามวงเงินงบประมาณ · ส่งออก GFMIS / e-GP |
| FR-18 | การรับเอกสารด้วยการสแกนและ AI | สแกนบิลและใบเสร็จ สกัดข้อมูล แสดงค่าความเชื่อมั่น บังคับยืนยันฟิลด์ที่เชื่อมั่นต่ำ และแจ้งเตือนความผิดปกติทางบัญชี |
| FR-19 | สิทธิ์และการควบคุมการเข้าถึง | บทบาท 8 ระดับ พร้อมขอบเขตข้อมูลรายบุคคล การซ่อนฟิลด์อ่อนไหว และการแยกหน้าที่ |

## 9. ความต้องการที่ไม่ใช่หน้าที่ (NFR)

| NFR-03 | ร่องรอยการตรวจสอบ | ทุกการเปลี่ยนแปลงต้องบันทึกผู้กระทำ เวลา และค่าก่อน–หลัง · ระบบต้องแยกให้ออกว่าใครเป็นผู้แก้ (ผู้ใช้ / ระบบอัตโนมัติ / API) |
| NFR-04 | ความถูกต้องของตัวเลข | จำนวนเงินต้องเป็นชนิดตัวเลขทศนิยม 2 ตำแหน่งเสมอ · ยอดรวมต้องมาจากการรวมบรรทัด ไม่ใช่คีย์เอง |
| NFR-05 | ความต่อเนื่องของลำดับ | ลำดับการเคลื่อนไหวในบัญชีแยกประเภทต้องต่อเนื่อง — เลขขาดหายถือเป็นเหตุการณ์ความผิดปกติ |
| NFR-06 | SLA ของกระบวนการ | อนุมัติใบสำคัญภายใน 1 วันทำการ · แจ้งเตือนเมื่อค้างเกินกำหนด · ปิดงวดภายใน 5 วันทำการหลังสิ้นเดือน |
| NFR-07 | เวลาและเขตเวลา | ทุกเวลาอ้างอิงเขตเวลา +07:00 · เวลาที่เป็นหลักฐานต้องมาจากเซิร์ฟเวอร์ ไม่ใช่เครื่องผู้ใช้ |
| NFR-08 | การเก็บรักษาข้อมูล | เอกสารทางบัญชีและไฟล์แนบเก็บอย่างน้อย 5 ปีตาม พ.ร.บ.การบัญชี |
| NFR-09 | สองภาษา | ข้อมูลหลักและงบการเงินต้องรองรับทั้งไทยและอังกฤษ |
| NFR-10 | แพลตฟอร์ม | ทุก business logic ต้องอยู่บน Nocoly เท่านั้น — ห้ามใช้สคริปต์หรือไฟล์ภายนอกเป็นส่วนหนึ่งของระบบที่ส่งมอบ |
| NFR-11 | ความสามารถในการตั้งค่า | อัตราภาษี กฎอนุมัติ กฎการออกเลขที่ และกฎการผ่านรายการ ต้องแก้ได้โดยผู้ดูแลข้อมูลหลัก ไม่ต้องพึ่งผู้พัฒนา |
| NFR-12 | การแยกหน้าที่ (SoD) | ผู้จัดทำ ผู้อนุมัติ และผู้ตั้งค่าระบบต้องเป็นคนละบทบาท และระบบต้องบังคับได้จริง |
| NFR-13 | การสำรองและกู้คืน | สำรองข้อมูลก่อนแก้โครงสร้างตารางทุกครั้ง · ล็อกแอปหลังขึ้นระบบจริง |

| A-05 | วงเงินอนุมัติและตารางมอบอำนาจ | **≤100,000 → AC-R2 · 100,001–1,000,000 → AC-R2 + AC-R3 · >1,000,000 → AC-R2 + AC-R3 + ผู้บริหาร** | สายอนุมัติในทุก workflow |

| A-07 | ต้องนำส่ง GFMIS หรือไม่ และรูปแบบใด | **ต้องนำส่ง แต่เลื่อนไปเฟสหลัง (Phase 10)** | ขอบเขตการเชื่อมต่อภายนอก |
| A-08 | จุดตัดข้อมูลและวันขึ้นระบบจริง | **ยังไม่กำหนด — ต้องได้ก่อนเริ่ม Phase 12** 🔴 (🆕 28 ส.ค. 2569: มีตาราง/ฟิลด์ให้ตั้งค่าได้แล้วในแอปตามคำขอผู้ใช้ — worksheet "พารามิเตอร์ระบบบัญชี" `6a917a2d9762533b5b720392` มีฟิลด์ `biz_cutover_date`/`biz_go_live_date` รอกรอกค่าจริง — **แต่ข้อสมมตินี้เองยังไม่ถูกยืนยัน ยังไม่มีการกรอกวันที่จริงแต่อย่างใด**) | การนำเข้ายอดยกมาและการทำคู่ขนาน |
| A-09 | องค์กรออกใบกำกับภาษีและใบเสร็จเองหรือไม่ และบัญชีเป็นเจ้าของหน้าที่นี้หรือไม่ | ✅ **ยืนยันแล้ว 28 ส.ค. 2569 — ไม่ใช่ บัญชีไม่ได้เป็นเจ้าของ** จะมีโมดูลการขายแยกต่างหากสร้างขึ้นภายหลัง และให้ฝ่ายขายเป็นผู้ออกเอกสารเอง (FR-12 ย้ายออกนอกขอบเขตถาวร) | **เกิดขึ้นจริงแล้ว 28 ส.ค. 2569** — FR-12 ย้ายออกนอกขอบเขตของโมดูลบัญชีทั้งก้อนตามที่คาดการณ์ไว้ (ราวหนึ่งในสี่ของโมดูล) จุดเชื่อมต่อในอนาคตคือรับรายการรายได้/ลูกหนี้จากโมดูลขายเข้ามาเท่านั้น (ดู §10) |
| A-10 | รับรู้ภาษีหัก ณ ที่จ่ายตอนตั้งหนี้ หรือตอนจ่าย | **ตอนจ่าย (At payment)** | ตัดสินว่าใบรับรองออกโดย WF-AC-06 หรือ WF-AC-14 และจุดรับรู้หนี้สิน |
| A-11 | การแบ่งหน้าที่สินทรัพย์ระหว่างบัญชีกับโมดูลสินทรัพย์ | ✅ **ยืนยันแล้ว 28 ส.ค. 2569 — บัญชีถือสมุดบัญชีสินทรัพย์ (`สมุดบัญชีสินทรัพย์`) เต็มรูปแบบ**: ราคาทุน อายุการใช้งาน มูลค่าซาก วิธีคิดค่าเสื่อม/ตารางค่าเสื่อม ค่าเสื่อมสะสม และกำไร/ขาดทุนจากการตัดจำหน่าย — **FR-13 อยู่ในขอบเขตเต็มรูปแบบ** โมดูลสินทรัพย์กายภาพ (ถ้าสร้างในอนาคต) จะถือเฉพาะการครอบครอง ตำแหน่ง และการตรวจนับ เชื่อมกันด้วยรหัสสินทรัพย์ร่วม ตรงกับ §4.2 | **เกิดขึ้นจริงแล้ว 28 ส.ค. 2569** — ไม่มีผลกระทบเปลี่ยนแปลงเพราะค่า default เดิมคือค่าที่ยืนยัน ตารางค่าเสื่อมและฟิลด์ทั้งหมดใน FR-13 พร้อมสร้างได้ทันทีที่ทีมจัดลำดับความสำคัญ |
| A-12 | ปริมาณเอกสารที่มาเป็นกระดาษเทียบกับมาจากจัดซื้อ | **ประมาณครึ่งต่อครึ่ง — เส้นทางสแกนเป็นเส้นทางหลัก** | กำหนดขนาดของบริการสกัดข้อมูล |
| A-13 | มีรายการสกุลเงินต่างประเทศหรือไม่ และใช้อัตราจากแหล่งใด | **มี · ใช้อัตราอ้างอิงธนาคารแห่งประเทศไทย บันทึกด้วยมือรายวัน** | FR-05 (อัตราแลกเปลี่ยน) และ WF-AC-22 |
| A-14 | ใช้บริการตรวจสอบเลขผู้เสียภาษีของกรมสรรพากรได้หรือไม่ | **ยังไม่ได้ — สร้างคู่ค้าด้วยมือ** | การสร้างคู่ค้าเป็นงานมือทั้งหมด |
| A-15 | อนุญาตให้ build agent ใช้ org-auth API กดอนุมัติแทนคนหรือไม่ | **ไม่อนุญาต** — ผู้อนุมัติต้องกดใน To-do เอง | ถ้าอนุญาตต้องมี test app + ที่เก็บ secret แยก |

**ข้อจำกัดเชิงเทคนิคที่ตกลงแล้ว**

1. ทุก business logic อยู่บน Nocoly เท่านั้น (NFR-10) — ไฟล์ภายนอกไม่ถือเป็นสิ่งส่งมอบ
2. แอปมีอยู่แล้วบนเซิร์ฟเวอร์ (**Brownfield**) — ห้ามสร้างตารางหรือฟิลด์ซ้ำ ต้องตรวจ ID Registry ใน Build Spec §1 ก่อนทุกครั้ง
3. การอนุมัติทำผ่าน MCP ไม่ได้ — ผู้อนุมัติต้องกดใน To-do จริง จึงจะถือว่าทดสอบครบวงจร
