## 1. WF-AC-33 ตัดยอดค้างรับเมื่อออกใบเสร็จรับเงิน · `6a9d2a302fe3e8d6b3b7cb9b` ✅ ทดสอบผ่าน

ปิดช่องว่างที่บันทึกไว้ใน `22-AR-Module.md` — เดิมต้องแก้ยอดค้างรับด้วยมือ

**Trigger** `worksheet_event / add_or_update` บนใบเสร็จรับเงิน · filter สถานะ = รับเงินแล้ว
**Nodes (11):** ค้นใบกำกับภาษี → **rollup sum เงินสดที่รับ** + **rollup sum ภาษีหัก ณ ที่จ่าย** จาก*ทุก*ใบเสร็จของใบกำกับนั้น → ยอดรับชำระสะสม = ผลรวมทั้งสอง → ยอดคงค้าง = ยอดรวม − รับชำระสะสม → อัปเดตใบกำกับ → ค้นใบแจ้งหนี้ต้นทาง → อัปเดตใบแจ้งหนี้ → branch: คงค้าง ≤ 0 → "รับชำระครบแล้ว" มิฉะนั้น "รับชำระบางส่วน"

**ทดสอบจริง 2 เส้นทาง** บน INV-2569/0029 (ยอดรวม 38,520):

| ขั้น | ที่ทำ | ผลบนใบกำกับ / ใบแจ้งหนี้ | สถานะ |

| 2 | รับชำระ 17,440 + หัก ณ ที่จ่าย 1,080 | รับแล้ว 38,520 · ค้าง 0.00 | รับชำระครบแล้ว ✓ |

`_updatedBy = user-workflow` ทุกครั้ง

### 🔴 บทเรียนที่ทำให้ต้องรื้อสร้างใหม่ — workflow ทำงานซ้ำแล้วยอดเพี้ยน

รอบแรกออกแบบเป็น **สะสม** (`ยอดรับเดิม + ยอดที่รับครั้งนี้`) ผลคือใบแจ้งหนี้ได้ยอด **40,000 และคงค้าง −1,480** ทั้งที่รับมาแค่ 20,000

สาเหตุ: **WF-AC-32 เขียนเลขใบสำคัญกลับลงใบเสร็จหลังทำงานเสร็จ** → เป็นการ update ใบเสร็จอีกครั้ง → **WF-AC-33 ถูกยิงซ้ำ**
`triggerFields: [สถานะ]` **ไม่ได้จำกัดให้ยิงเฉพาะตอนฟิลด์นั้นเปลี่ยน** — update ฟิลด์ไหนก็ยิง

**ทางแก้ที่ใช้: ทำให้ idempotent แทนการกันไม่ให้ยิงซ้ำ** — เปลี่ยนจาก "บวกเพิ่ม" เป็น **"รวมยอดจากใบเสร็จทั้งหมดใหม่ทุกครั้ง" (rollup)** ยิงกี่รอบผลก็เท่าเดิม
ยืนยันด้วยการอ่านค่าซ้ำหลังยิง 2 รอบ ค่าไม่ขยับ · บันทึกเป็น **D-59**

## 2. WF-AC-30 รวมยอดและภาษีขายขึ้นหัวใบแจ้งหนี้ · `6a9d2b34b6bb30e62dc34737` ✅ ทดสอบผ่าน

ปิด **AC-R-23** — เดิมยอดภาษีขายบนหัวใบแจ้งหนี้มาจากสคริปต์ ถ้าผู้ใช้คีย์เองจะไม่ถูกคิดให้

**Trigger** `add_or_update` บนรายการรายได้
**Nodes (9):** ค้นใบแจ้งหนี้ต้นทาง → **branch กันแก้เอกสารที่ผ่านรายการแล้ว** → rollup sum มูลค่าที่ต้องเสียภาษี / ภาษีขาย / จำนวนเงินรวม → มูลค่าที่ไม่ต้องเสียภาษี = รวม − ต้องเสียภาษี → ยอดรวม = รวม + ภาษี − ส่วนลดท้ายบิล → ยอดคงค้าง = ยอดรวม − รับชำระแล้ว → เขียนขึ้นหัว 5 ฟิลด์

**ทดสอบ:** ใบแจ้งหนี้ร่าง + 2 บรรทัด (100,000 มีภาษี / 50,000 ไม่มีภาษี)
→ ได้ ต้องเสียภาษี 100,000 · ไม่ต้องเสียภาษี 50,000 · VAT 7,000 · รวม 157,000 · ค้าง 157,000 **ตรงทุกช่อง**
**ทดสอบด่านกันแก้:** ตั้ง flag "รับรู้รายได้แล้ว" = 1 แล้วแก้บรรทัดเป็น 999,999 → ยอดบนหัว **ไม่ขยับ** ✓

⚠️ **เลี่ยง D-43 โดยตั้งใจ** — เดิมจะเขียน branch เป็น OR (สถานะ = ร่าง **หรือ** รออนุมัติ) แต่ D-43 บอกว่า OR group ใน branch ไม่ถูกใช้จริง
จึงเปลี่ยนเป็นเงื่อนไขเดี่ยวเชิงบวก: **flag "รับรู้รายได้แล้ว" = "1" → ข้าม** ที่เหลือตกลง fallback

## 3. WF-AC-07 คิดค่าเสื่อมราคาประจำเดือน · `6a9d2c478475f61d4c7327d9` (สายลูก `6a9d2c5a8475f61d4c73287d`) ⚠️ publish แล้ว ยังไม่ได้ยิงจริง

**Trigger** `schedule` รายเดือน 23:00 · **ยิงทดสอบผ่าน API ไม่ได้** ต้องกด "Execute now" บนหน้าเว็บ (ตามที่สเปก FR-13 ระบุไว้แต่แรก)
**สายแม่ (3 nodes):** หางวดบัญชีที่เปิดอยู่ล่าสุด → ดึงสินทรัพย์ที่ใช้งานอยู่ → `sub_process` วนทีละรายการ
**สายลูก (8 nodes):** **กันซ้ำ** (rollup sum ค่าเสื่อมที่บันทึกงวดนี้แล้ว → ถ้า > 0 ข้าม) → ค่าเสื่อม = (ราคาทุน − มูลค่าซาก) ÷ อายุ ÷ 12 → ค่าเสื่อมสะสม → มูลค่าสุทธิ → **กันคิดเกินมูลค่า** (ถ้ามูลค่าสุทธิ < 0 ข้าม) → สร้างแถวตารางค่าเสื่อม → อัปเดตทะเบียนสินทรัพย์

🔑 **ด่านกันซ้ำจำเป็นจริง ๆ** — ชุดข้อมูลปัจจุบันบันทึกค่าเสื่อมถึงงวด 2569-12 (ก.ย. 2026) ไว้แล้ว ถ้า schedule ยิงวันที่ 30 ก.ย. โดยไม่มีด่านนี้จะคิดซ้ำทั้งเดือน · ด่านใช้คีย์ `งวด · รหัสสินทรัพย์` ซึ่งไม่ซ้ำกันอยู่แล้ว

⚠️ **`rollup method:"count"` และ `"filled"` ใช้ไม่ได้** — `count` บังคับต้องมี `config.target` (นับ record จาก node ต้นทางเท่านั้น) ส่วน `filled` ถูกปฏิเสธว่าไม่อยู่ใน enum
ทั้งที่ schema เขียนว่ารองรับ ⇒ ใช้ **`sum` บนฟิลด์จำนวนเงินแล้วเทียบ > 0** แทน · บันทึกเป็น **D-60**

**ยังไม่ได้ทำ:** ออกใบคิดค่าเสื่อมและใบสำคัญเข้า GL อัตโนมัติ — สเปกกำหนดให้**จัดกลุ่มตามประเภทสินทรัพย์ + หน่วยงาน** ซึ่ง workflow บนแพลตฟอร์มนี้ไม่มี node สำหรับ group-by ⇒ ทำได้แค่ผูกตายตัวรายประเภท ซึ่งจะพังทันทีที่เพิ่มประเภทใหม่ · **ไม่ทำแบบเดา** เปิดเป็น AC-R-33
