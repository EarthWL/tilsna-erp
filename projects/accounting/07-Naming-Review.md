# ตรวจทานชื่อ Worksheet และ Field — โมดูลบัญชี TILSNA ERP

> ตรวจจากโครงสร้างจริงบนแอป `ERP - TILSNA` เมื่อ 26 ส.ค. 2569 · ครอบคลุม 34 worksheet · 404 ฟิลด์ธุรกิจ
> เกณฑ์ตรวจ: **คนบัญชีเปิดหน้าจอแล้วอ่านรู้เรื่องไหม** และ **ชื่อสื่อความหมายตรงกับสิ่งที่ฟิลด์เก็บจริงไหม**

---

## บทสรุปสำหรับผู้บริหาร

ปัญหาไม่ได้อยู่ที่ "ชื่อไม่สวย" แต่มี **2 เรื่องที่ต่างกันคนละชั้น** และควรแก้คนละแบบ

| # | ปัญหา | ความรุนแรง | ความเสี่ยงถ้าแก้ |
|---|---|---|---|
| **1** | **ชื่อที่แสดงบนหน้าจอเป็นภาษาอังกฤษเชิงเทคนิคทั้งหมด** — คนบัญชีเปิด "ใบสำคัญตั้งหนี้" แล้วเห็นหัวคอลัมน์ว่า `ap_no`, `taxable_base`, `doc_discount` | สูง (กระทบผู้ใช้ทุกคน ทุกวัน) | **ไม่มี** — แก้เฉพาะชื่อที่แสดง ไม่แตะ alias หรือ field ID |
| **2** | **ชื่อ 8 จุดสื่อความหมายผิด** ไม่ว่าจะภาษาไหน — เช่น ฟิลด์ที่ขึ้นต้น `is_` แต่ไม่ใช่ใช่/ไม่ใช่ · ฟิลด์ชื่อ `vat_name` ที่ไม่ได้เก็บชื่อ | สูง (ทำให้คนอ่าน spec เข้าใจผิด) | ต่ำ–ปานกลาง |
| **3** | ชื่อซ้ำซ้อน/คลุมเครือเชิงโครงสร้าง 5 จุด — ไม่ใช่เรื่องชื่อ แต่เป็นเรื่องแบบจำลองข้อมูล | ปานกลาง | ต้องตัดสินใจเชิงออกแบบก่อน |

**ข้อสังเกตที่สำคัญที่สุด:** ระบบนี้ **มีศัพท์บัญชีไทยที่ถูกต้องอยู่แล้ว — แต่อยู่ในข้อมูล ไม่ใช่ในโครงสร้าง**

- `AC_DOC_TYPE` มีข้อมูลว่า **ใบสำคัญทั่วไป · ใบสำคัญตั้งหนี้ · ใบสำคัญจ่าย · ใบขออนุมัติเบิกจ่าย · ใบวางบิล · ใบกำกับภาษี/ใบส่งของ · ใบเสร็จรับเงิน · ใบลดหนี้ · ใบเพิ่มหนี้ · หนังสือรับรองการหักภาษี ณ ที่จ่าย · ใบสำคัญกลับรายการ · ใบสำคัญปรับปรุงสิ้นงวด**
- `AC_JOURNAL` มี **สมุดรายวันทั่วไป · ซื้อ · ขาย · รับเงิน · จ่ายเงิน**
- `AC_COA` มี `account_name_th` · `AC_WHT_INCOME_TYPE` มี `description_th`

⇒ **คำศัพท์ที่ถูกต้องมีอยู่แล้ว** เพียงแต่ชั้นโครงสร้าง (ชื่อตาราง/ชื่อฟิลด์) ยังไม่ได้ใช้คำเดียวกัน ข้อเสนอทั้งหมดในเอกสารนี้จึง **ยืมคำจากข้อมูลที่มีอยู่** ไม่ได้คิดคำใหม่

## 2. ปัญหาชั้นที่ 2 — ชื่อที่สื่อความหมายผิด (ควรแก้ทั้ง name และ alias)

> ทั้ง 8 ข้อนี้ **ไม่ใช่เรื่องภาษา** — ต่อให้เขียนเป็นอังกฤษก็ยังผิด และทำให้คนอ่าน spec หรือ agent ที่มาทำต่อเข้าใจผิดได้

### 2.1 🔴 `AC_VOUCHER.status` มี alias เป็น `status1`

ชื่อกับ alias ไม่ตรงกัน เขียนค่าลง `status` จะเงียบไม่มี error (เคยทำให้เสียเวลาแล้วจริงในรอบสร้าง workflow)
**เสนอ:** เปลี่ยน alias เป็น `voucher_status` — workflow ทั้งหมดอ้างด้วย field ID จึงไม่กระทบ

### 2.2 🔴 `AC_PARTNER.is_domestic` — ขึ้นต้น `is_` แต่ไม่ใช่ใช่/ไม่ใช่

เป็น SingleSelect 2 ค่า (Domestic / Foreign) ไม่ใช่ Checkbox · ฟิลด์อื่นในระบบที่ขึ้นต้น `is_` ล้วนเป็น Checkbox จริง (`is_active`, `is_postable`, `is_base`)
**เสนอ:** `partner_residence` · ชื่อไทย **ถิ่นที่อยู่ (ในประเทศ/ต่างประเทศ)**

### 2.3 🔴 `AC_VAT_RATE.vat_name` — ไม่ได้เก็บ "ชื่อ"

เก็บ **ประเภทการเสียภาษี** (Standard-rated / Zero-rated / Exempt / Non-VAT) ซึ่งเป็นการจัดประเภททางกฎหมาย ไม่ใช่ชื่อเรียก
**เสนอ:** `vat_treatment` · ชื่อไทย **ประเภทการเสียภาษีมูลค่าเพิ่ม**

### 2.4 🔴 `AC_VAT_RATE.is_taxable_base` — อ่านแล้วเข้าใจกลับด้าน

ชื่ออ่านว่า "ฟิลด์นี้คือฐานภาษี" แต่ความหมายจริงคือ "อัตรานี้ **นับรวมเข้า**ฐานภาษีหรือไม่"
**เสนอ:** `counts_in_taxable_base` · ชื่อไทย **นับเป็นฐานภาษีมูลค่าเพิ่ม**
> ฟิลด์นี้เป็นตัวที่ทำให้ **TC-16** (เอกสารมีหลายอัตราปนกัน) ผ่านได้ — ตั้งชื่อผิดคือความเสี่ยงจริง

### 2.5 🟡 `AC_GL.debit_thb` / `credit_thb` — ฝังชื่อสกุลเงินไว้ในโครงสร้าง

ระบบออกแบบให้รองรับหลายสกุลเงินและมี `AC_CURRENCY.is_base` เป็นตัวกำหนดสกุลเงินฐานอยู่แล้ว การใส่ `thb` ในชื่อทำให้ถ้าวันหนึ่งสกุลเงินฐานเปลี่ยน ชื่อจะโกหก
**เสนอ:** `debit_base` / `credit_base` · ชื่อไทย **เดบิต (เงินบาท)** / **เครดิต (เงินบาท)** — เก็บ "เงินบาท" ไว้ในชื่อที่แสดงได้ เพราะแก้ง่าย แต่ alias ไม่ควรผูกสกุลเงิน

### 2.6 🟡 `AC_VAT_DOC.sign` — ตัวเลข +1/−1 ที่ไม่มีคำอธิบาย

คนบัญชีเปิดมาเห็นคอลัมน์ `sign` มีค่า 1 กับ −1 จะเดาไม่ออก
**เสนอ:** `sign_factor` · ชื่อไทย **ทิศทางรายการ (+1 ปกติ / −1 กลับรายการ)**

### 2.7 🟡 `wht_type` ชี้ไปที่ "ประเภทเงินได้" ไม่ใช่ "ประเภทภาษี"

`AC_ITEM.wht_type` และ `AC_AP_LINE.wht_type` เป็น Relation → `AC_WHT_INCOME_TYPE` ซึ่งคือ **ประเภทเงินได้** ตามแบบ ภ.ง.ด. ไม่ใช่ประเภทของภาษี
**เสนอ:** `wht_income_type` · ชื่อไทย **ประเภทเงินได้**

### 2.8 🟡 ชื่อ "ตัวหลัก" ของเอกสารใช้คำว่า `_ref` ทั้งที่เป็นเลขที่ของตัวเอง

`AC_PAY_LINE.line_ref` · `AC_PAY_SETTLE.settle_ref` · `AC_VAT_DOC.vat_doc_ref` เป็นฟิลด์ชื่อเรื่อง (isTitle) ของ record ตัวเอง แต่คำว่า `ref` ในระบบนี้ที่อื่นหมายถึง "อ้างอิงไปหาของอื่น" (`po_ref`, `gr_ref`, `budget_ref`, `reference_no`)
**เสนอ:** เปลี่ยนเป็น `_no` ให้เข้าชุดกับ `voucher_no` / `ap_no` / `pay_no` / `wht_no`

## 4. ข้อเสนอมาตรฐานการตั้งชื่อ (ใช้กับของใหม่ทั้งหมด)

| หัวข้อ | มาตรฐานที่เสนอ |
|---|---|
| **ชื่อที่แสดง (`name`)** | ภาษาไทย ศัพท์บัญชี/ศัพท์ราชการ · ฟิลด์ที่ผู้ใช้ห้ามแก้ ขึ้นต้นด้วย **(ระบบ)** |
| **alias** | อังกฤษ `snake_case` · ของใหม่ใช้รูปแบบ `biz_<ตัวย่อตาราง>_<ชื่อ>` (แพลตฟอร์มบังคับให้ขึ้นต้น `biz_`) |
| **เลขที่เอกสาร** | ลงท้าย `_no` เสมอ (`voucher_no`, `ap_no`, `pay_no`) — ห้ามใช้ `_ref` |
| **การอ้างอิงถึงเอกสารอื่น** | ลงท้าย `_ref` (`po_ref`, `gr_ref`) หรือใช้ Relation ตรง ๆ |
| **ค่าใช่/ไม่ใช่** | ขึ้นต้น `is_` และ **ต้องเป็น Checkbox เท่านั้น** |
| **ฟิลด์ธงของระบบ** | ลงท้าย `_flag` · ชนิด Number · **ตั้ง default 0 เสมอ** |
| **วันที่/เวลา** | ลงท้าย `_date` (Date) หรือ `_at` (DateTime) |
| **จำนวนเงิน** | ไม่ใส่ชื่อสกุลเงินใน alias · ใช้ `_base` ถ้าหมายถึงสกุลเงินฐาน |
| **สถานะ** | `<ตาราง>_status` และผูกกับ optionset เสมอ ห้ามเป็น Text |

## 5. สิ่งที่ตรวจแล้วว่า **ถูกต้องดีอยู่แล้ว** (อย่าไปแก้)

- `AC_VOUCHER_LINE.debit` / `credit` — ตรงศัพท์บัญชี ไม่ต้องเปลี่ยน
- `AC_VAT_DOC.tax_point_date` แยกจาก `tax_invoice_date` — เป็นการแยกที่ถูกต้องตามประมวลรัษฎากร และเป็นหัวใจของ v2.0
- `AC_AP_LINE.wht_rate` เป็น Number (สำเนาอัตรา) ไม่ใช่ lookup — ถูกต้อง เอกสารเก่าจะคงอัตราที่ใช้ตอนนั้น
- `AC_PERIOD` แยก `period_status` กับ `tax_period_status` — ถูกต้อง งวดบัญชีกับงวดภาษีปิดคนละเวลา
- `AC_COA.require_cost_center / _fund / _project / _partner` — ชื่อสื่อความหมายชัดเจนดี
- `AC_DOC_NUMBER_RULE.year_era` (CE/BE) — รองรับ พ.ศ. ตามที่เอกสารราชการต้องการ
- รหัสตาราง `AC_*` ทั้งหมด — เป็นรหัสเทคนิคที่ดี **ควรเก็บไว้** เพียงเพิ่มชื่อไทยสำหรับแสดงผล
