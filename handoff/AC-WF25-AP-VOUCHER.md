## 🔴 อ่านข้อนี้ก่อน — น่าจะกระทบ workflow ที่ฝั่ง HR เขียนไว้ด้วย

### เขียนฟิลด์ Relation ด้วย `{kind:"record", node:{...}}` **ไม่ได้**

ระบบจะเก็บเป็น **สตริง `["<nodeId>"]`** ลงไปตรง ๆ แล้วแสดงเป็น **`已删除`**

**อาการที่เห็น:** ใบสำคัญออกมา **ยอดรวมเดบิต/เครดิต = 0.00** ทั้งที่บรรทัดถูกสร้างครบ 6 บรรทัดพร้อมจำนวนเงินถูกต้องทุกบาท — เพราะบรรทัดไม่ได้ผูกกับใบสำคัญจริง
**นี่คืออาการเดียวกับ D-shape C ใน `handoff/AC-RELATION-AUDIT.md`** ที่เคยทำ `ac_gl.voucher` พังทั้งตาราง — แค่คราวนี้มาจากการเขียนผ่าน MCP แทนที่จะมาจากหน้าจอ

| ใช้ที่ไหน | `kind:"record"` |
|---|---|
| `config.target` ของ update_record / delete_record / approval | ✅ ถูกต้อง จำเป็นต้องใช้ |
| `config.fields[].value` ที่เขียนลงฟิลด์ Relation | 🔴 **ห้ามใช้** — ต้องใช้ `{kind:"field", node:X, fieldId:"rowid"}` |

⚠️ **`validate_process` ไม่จับข้อนี้** และ workflow รันจนจบโดยไม่มี error — ตรวจได้ทางเดียวคือ**เปิดดูข้อมูลที่เขียนออกมาจริง** แล้วดูว่าฟิลด์ relation ขึ้น `已删除` หรือไม่
⇒ **ขอให้ฝั่ง HR ไล่ดู workflow ที่เขียนฟิลด์ relation ทุกตัว** (ผูกใบลาเข้าพนักงาน · ผูกรายการสลิปเข้าสลิป · ผูกใบ OT เข้าใบขออนุมัติ) ว่าเขียนด้วยรูปแบบไหน

### branch ไม่มีจุดบรรจบ

สายที่แยกแล้ว **ไม่กลับมารวมกัน** ⇒ โหนดที่ต้องทำงานหลัง branch ต้องทำซ้ำในทุกสาย
**วิธีเลี่ยงที่ใช้ได้ผล:** ให้ `code` node คืน *ค่าที่ใช้ค้นหา* (เช่นรหัสบัญชี) แล้วใช้ `get_single` ไปหยิบ record มา ⇒ เหลือ branch ชั้นเดียวแทนที่จะซ้อนสองชั้นแล้วทำโหนดปลายทางซ้ำ 4 ชุด

### AutoNumber ให้ปีคริสต์ศักราชเท่านั้น

`createdTime` format `yyyy` ให้ `2026` ไม่ใช่ `2569` และไม่มีตัวเลือกปี พ.ศ. · เอกสารที่ต้องใช้ปี พ.ศ. ในเลขที่ต้องให้ code node ออกเลขเอง
อีกข้อ: AutoNumber เดินเลขให้ **ทุกแถวในตาราง** ไม่ใช่เฉพาะแถวที่ workflow สร้าง ⇒ ถ้าเอกสารหลายชนิดใช้ตารางเดียวกัน เลขจะมีช่องว่าง

## สิ่งที่ตัวงานเองได้มา

**เส้นทาง "ใบตั้งหนี้ → ใบสำคัญ → บัญชีแยกประเภท" เป็นอัตโนมัติแล้ว** — เดิมต้องสร้างใบสำคัญด้วยมือ (ดู `16-Demo-AP-to-GL.md`)

ระบบเลือกบัญชีเองถูกทั้งสองจุดที่เคยต้องให้คนตัดสิน:
- **ภาษีซื้อ** `110301` เมื่อติ๊กว่าได้รับใบกำกับแล้ว · `110302` ภาษีซื้อรอเรียกคืนเมื่อยังไม่ได้รับ
- **ภาษีหัก ณ ที่จ่าย** อนุมานจากคู่ค้า: ต่างประเทศ → ภ.ง.ด.54 `210303` · นิติบุคคลในประเทศ → ภ.ง.ด.53 `210302` · บุคคลธรรมดา → ภ.ง.ด.3 `210301`

**ตัดงาน 3.5 ตรงรอยต่อที่สเปกเขียนไว้เอง** — `14-FRS-Modules-AC.md` §2 FR-07.1 ระบุว่า Approve node เขียนสถานะเป็น "รับรู้แล้ว" แล้วจึงสร้างใบสำคัญ ⇒ WF-AC-25 รับช่วงตั้งแต่จุดนั้น จึงทดสอบได้เต็มรูปแบบโดยไม่ต้องรอสมาชิก role และเมื่อสายอนุมัติสร้างเสร็จก็ต่อกันได้ทันที
