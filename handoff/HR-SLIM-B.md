## 1. ตอบคำถามข้อ 1 — `conditionId 9` (`=`) เพี้ยนกับค่าว่างไหม

**คำตอบสั้น: ไม่อันตราย แต่ด้วยเหตุผลที่ต้องเข้าใจให้ถูก**

> 🔴 **แก้ไขฉบับนี้ 31 ส.ค. 2569 (จาก `/scrutinize`)** — ข้อความเดิมของหัวข้อนี้เขียนสมมติฐานว่า *"เงื่อนไขที่เทียบกับฟิลด์ว่างคืน FALSE เสมอ **ไม่ว่า operator จะเป็นอะไร**"* ซึ่ง **ขัดกับตารางในย่อหน้าถัดมาของตัวเอง** ที่ระบุว่า `8` คืน TRUE — และ `8` คือฐานของการแก้ D-19 ทั้งหมด · ถ้าอ่านตามตัวอักษรจะสรุปได้ว่าการแก้ใช้ไม่ได้ตั้งแต่ต้น · **ข้างล่างคือฉบับที่ถูกต้อง**

**แบบจำลองที่อธิบายหลักฐานได้ทั้งหมด — ต้องแยก operator เป็น 2 ชนิด**

| ชนิด | operator | ทำงานกับอะไร | เจอค่าว่างแล้วเป็นยังไง |
|---|---|---|---|
| **เทียบค่า** | `9` (`=`) · `10` (`≠`) · `<` `≤` `not_in` … | ตัว**ค่า**ในฟิลด์ | **คืน FALSE** — ไม่มีค่าให้เทียบ |
| **ทดสอบการมีอยู่** | `7` (ไม่ว่าง) · `8` (ว่าง) | ตัว**ฟิลด์** ว่ามีค่าหรือไม่ | **ทำงานถูกต้องปกติ** |

⇒ ผลที่ตามมา:

| operator | ค่าที่ควรได้เมื่อฟิลด์ว่าง | ค่าที่ได้จริง | อันตรายไหม | หลักฐาน |
|---|---|---|---|---|
| `9` (`=`) | FALSE | FALSE | 🟢 **ไม่** — บังเอิญตรงกับที่ตั้งใจ | `[S]` อ่านโครง + พฤติกรรมที่สังเกตได้ |
| `10` (`≠`) | **TRUE** | **FALSE** | 🔴 **ใช่ — นี่คือ D-19** | **`[V]` A/B controlled test** (record E/F) |
| `8` (ว่าง) | TRUE | **TRUE** | 🟢 ไม่ — **ใช้เป็นทางแก้ได้** | **`[V]` ยิงจริง 2 ครั้ง** ⬇︎ |
| `7` (ไม่ว่าง) | FALSE | FALSE | 🟢 ไม่ | `[S]` |

🔴 **`8` = TRUE กับค่าว่าง พิสูจน์ด้วยการยิงจริงแล้ว 2 ครั้ง ไม่ใช่แค่อ่านโครง** — สำคัญเพราะเป็นฐานของการแก้:

1. **WF-HR-02** · record `TEST-LR-D19-G` (`deducted_flag` = ว่าง) → Approved → **ตัดสิทธิสำเร็จ** (used 0→1) · กลุ่ม OR ที่ 1 (`≠ "1"`) เป็นเท็จแน่นอนสำหรับค่าว่าง (พิสูจน์ด้วย record F ก่อนหน้า) ⇒ **ตัวที่ทำให้ยิงคือกลุ่มที่ 2 ซึ่งใช้ `8`**
2. **WF-HR-03** · record เดียวกัน (`returned_flag` = ว่าง) → Cancelled → **คืนสิทธิสำเร็จ** (used 1→0) ⇒ ยืนยันซ้ำอีกตัว

⇒ **กฎที่ใช้คัดกรองได้เร็ว: operator ไหนก็ตามที่ "คำตอบที่ถูกต้องสำหรับค่าว่าง คือ TRUE" ตัวนั้นอันตราย** ไม่ใช่แค่ `10`

**ดังนั้นแนะนำให้ทางนั้นสแกนเพิ่มอีกกลุ่ม** — operator เชิงปฏิเสธ/ช่วงที่ยังไม่ได้ไล่ เช่น `not_in` · `<` / `≤` (ถ้าเจตนาคือ "ยังไม่ถึงเกณฑ์" ค่าว่างควรนับด้วย) · และเงื่อนไขวันที่แบบ "ก่อนวันที่ X"

### ⚠️ ข้อจำกัดที่ต้องรู้ก่อนใช้ `8` กับ node ชนิด get_multiple — **ที่ผมลืมเขียนในฉบับแรก**

หลักฐานทั้ง 2 ชิ้นข้างบนเป็น **branch (typeId 2) เท่านั้น** · **`8` ใน `filters` ของ node ชนิด search(7)/get_multiple(13) ยังไม่เคยพิสูจน์เลยสักครั้ง**

🔴 **ข้อเสนอ: แก้ 2 จุดที่เป็น branch ก่อน (พิสูจน์แล้ว ปลอดภัย) แล้วค่อยแก้ 2 จุด get_multiple แยกรอบพร้อมแผนพิสูจน์**
สำหรับ get_multiple ฝั่งบัญชี **พิสูจน์ง่ายกว่าของผม** เพราะไม่ใช่ schedule — สร้าง record 2 ใบที่ต่างกันแค่ธง `'0'` vs `''` แล้วดูว่า node เลือกได้กี่ใบ (ผ่าน Workflow History หรือดูผลปลายทาง) · **ถ้าทางนั้นพิสูจน์ได้ ช่วยบอกกลับด้วย จะได้อัปเป็น `[V]` แล้วผมจะปิด WF-HR-05 ตามได้เลย**

## 2. ตอบคำถามข้อ 2 — **ต้อง `publish` ทุกครั้ง**

ผม `hap workflow publish <processId>` หลัง `node save` ทุกครั้งครบทั้ง 5 process และเห็น **version เลื่อนตอน publish** (WF-HR-05 ไป v2 แล้ว v3)

> ⚠️ **สิ่งที่ผมยังไม่ได้ทดสอบ:** ว่า `node save` เฉย ๆ โดยไม่ publish นั้น **มีผลกับ instance ที่ยิงใหม่หรือไม่** — ผม publish ทันทีทุกครั้งจึงแยกไม่ออก
> ⇒ **ข้อแนะนำที่ปลอดภัย: publish เสมอ** และเช็คหลัง publish ด้วย `hap workflow get <id>` ว่า `enabled=true` `deleted=false` และ version เลื่อนจริง

**และเตือนซ้ำอีกรอบสำหรับ node ชนิด get_multiple (13) ที่ทางนั้นเจอ 2 จุด:**

1. `hap workflow node save-get-more --condition '[[A],[B]]'` → `rc=0` ตอบ `saved.` แต่ **เก็บแค่ group แรก ทิ้ง B เงียบ ๆ** + รีเซ็ต `relation` `true`→`false` และ `filters[0].spliceType` `1`→`2` โดยไม่ได้ขอ
2. `hap workflow node save --type 13 -c '{"filters": …}'` (ส่งคีย์เดียวแบบที่ใช้กับ branch ได้) → **500 Internal Server Error**
3. ✅ **ที่ใช้ได้จริง:** `node save --type 13` ส่ง config ที่เขียนได้**ครบทั้งก้อน** — `actionId` `appId` `appType` `name` `desc` `fields` `sorts` `numberFieldValue` `execute` `relation` `random` `conditions` `filters`
4. **หลัง save ต้องอ่านกลับเทียบทีละคีย์** ไม่ใช่ดูแค่เงื่อนไข — ผมจับ `relation`/`spliceType` ที่เพี้ยนได้จากขั้นนี้ แล้วคืนค่าเดิม
