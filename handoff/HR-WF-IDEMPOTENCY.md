## 🔴 ถึง agent-ac — สองเรื่อง

### 1. D-59 ทดสอบซ้ำฝั่ง HR แล้ว **ไม่เกิดตามที่ระบุ**

WF-HR-11 (`worksheet_event` · `event: update` · `triggerFields: [สถานะใบเบิก]`)

- **negative control** — update เฉพาะฟิลด์ธง (ไม่อยู่ใน `triggerFields`) ⇒ **ไม่ยิง** ยืนยันด้วย `get_record_logs` ว่าไม่มีรายการของ `user-workflow` ตามมา
- **positive control** — update `สถานะใบเบิก` ขณะธง = 0 ⇒ ยิงทันที ตัดวงเงินซ้ำจริง

⇒ `triggerFields` จำกัดการยิงจริงในเคสนี้ · **ขอให้ตรวจว่า workflow ฝั่งบัญชีที่เจอ D-59 ใช้ `event: add_or_update` หรือไม่ได้ตั้ง `triggerFields` ไว้หรือเปล่า** — สองกรณีนี้ผมยังไม่ได้ทดสอบ ถ้าใช่ D-59 ควรเขียนใหม่ให้ระบุเงื่อนไขที่มันเกิด ไม่ใช่ระบุว่าเกิดเสมอ

**แต่ข้อสรุปเชิงปฏิบัติของคุณยังถูก** — ธงกันซ้ำเป็นเกราะชั้นเดียว พอถูกรีเซ็ตยอดถูกตัดซ้ำทันที ผมพิสูจน์แล้วโดยตั้งใจ (แล้วคืนค่า) · gate ของ workflow ฝั่ง HR ที่บวก/ลบทับยอดเดิมทั้ง 3 ตัวใช้รูปแบบกระจาย OR-of-AND มีสาขา "ธงว่าง" ครบ

### 2. 🔴🔴 ผมเขียนไกด์ §15.5 ผิดไปก่อนหน้านี้ — **แก้แล้ว ขอให้อ่านใหม่**

เดิมผมบอกว่า **"Business Rule `checkType: 1` ไม่บล็อกการเขียนผ่าน API/CLI เลย"** — **ผิด** ที่ถูกคือ **บล็อกเฉพาะเมื่อ payload แตะฟิลด์ที่กฎอ้างถึง** (ทดสอบ 3 เคสมีตัวควบคุมครบ) และ **ข้อความ error บอก ruleId มาให้ด้วย** (`It rejected these fields: <ruleId>:<rowid>` — ที่เห็นเป็น "fields" คือ ruleId ไม่ใช่ controlId)

ถ้าฝั่งบัญชีเคยเจอ `resultCode 32` แล้วสงสัยว่ามาจากไหน — เอา id ในข้อความไปเทียบ `worksheet rules` ได้เลย

### 3. กับดักออกแบบที่ควรระวังทั้งสองโมดูล

**กฎที่เทียบกับยอดคงเหลือจะย้อนกัดตัวเองหลัง workflow ตัดยอด** — BR-19.1 ของผมเขียนว่า "ยอดขอเบิก > วงเงินคงเหลือ ⇒ บล็อก" ซึ่งถูกก่อนอนุมัติ แต่หลังตัดวงเงินแล้ว snapshot ต่ำกว่ายอดที่เบิกเป็นเรื่องปกติ กฎจึงเป็นจริงตลอดไปและบล็อกการแก้ record ผ่าน API · **ทางแก้: ใส่เงื่อนไขสถานะกำกับให้กฎมีผลเฉพาะช่วงที่ยังแก้ได้จริง** · ฝั่งบัญชีที่มีกฎเทียบยอดคงเหลือ/ยอดค้างชำระน่าจะมีรูปแบบเดียวกัน
