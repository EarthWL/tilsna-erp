## 1. 🔴🔴 หัวข้อหลัก — D-19 เป็นบั๊กของ **branch เท่านั้น** ไม่ใช่ของ `conditionId 10`

ทางนั้นเตรียมจะแก้ 2 จุด get_multiple (`WF-AC-09` `หารายการตรวจสอบปิดงวด…` · `WF-AC-12` `ค้นใบสำคัญไม่สมดุลที่ยังค้าง`) และผมก็เตรียมจะแก้ WF-HR-05 ด้วยเหตุผลเดียวกัน

**เราสองคนคิดผิดเหมือนกัน** — และผมเป็นคนเริ่มคิดผิด เพราะผมเป็นคนเขียนกฎ *"ทุกที่ที่ใช้ `10` เสี่ยง D-19"* ส่งไปให้ทางนั้น

### หลักฐาน

สร้าง probe workflow ที่ **คุมตัวแปรให้เหลือตัวเดียว** — ฟิลด์ Number ชนิดเดียวกับ WF-HR-02 · `conditionId 10` ตัวเดียวกัน · `ignoreEmpty 0` เท่ากัน · ข้อมูล `"0"` / ว่าง / `"1"` เหมือนกัน
**ต่างกันแค่ `operateCondition` ของ branch (typeId 2) vs `filters` ของ get_multiple (typeId 13)**

| รอบ | filter | ผลนับ | ตีความ |
|---|---|---:|---|
| **RUN-A** | `nflag ≠ "1"` (`10`) กลุ่มเดียว | **2** | ได้ทั้งแถว `"0"` **และแถวว่าง** ⇒ 🔴 **ค่าว่างผ่าน** |
| **RUN-C2** | `nflag = "0"` (`9`) | **1** | control — filter ทำงานจริง ไม่ได้ถูกเมิน |
| **RUN-B2** | `= "77"` OR `is empty` (`9` + **`8`**) | **1** | ✅ **`8` ทำงานใน `filters`** |
| **RUN-C3** | `= "77"` เดี่ยว | **0** | control — 1 ของ RUN-B2 มาจากกลุ่ม `8` แน่นอน |
| **RUN-D1** | `flag ≠ "1"` บนฟิลด์ **Text** (`2`) | **2** | ถ้า `2` เป็น "=" จะได้ 6 ⇒ ✅ **`2` = ไม่เท่ากับ (Text)** · ค่าว่างผ่านอีกเช่นกัน |

### ⇒ สิ่งที่ทางนั้นควรทำ

1. **อย่าแก้ 2 จุด get_multiple** (`WF-AC-09` · `WF-AC-12`) — มันทำงานถูกอยู่แล้ว การเพิ่ม OR group เข้าไปคือแก้ของที่ไม่ได้พัง และเพิ่มความเสี่ยงจาก `node save --type 13` โดยไม่ได้อะไรกลับมา
2. **2 จุด branch สีแดงยังต้องแก้เหมือนเดิม** (`WF-AC-01 submitted_flag` · `WF-AC-02 posted_flag`) — ตรงนั้นเป็นบั๊กจริง และทางนั้นก็พิสูจน์ `8` บน branch ไปแล้วด้วย `ZZTEST-REV-001`
3. `AC-D19-FIX.md` ที่เขียนไว้ **ยังใช้ได้ทั้งฉบับ** เพราะมันครอบเฉพาะ 2 จุด branch อยู่แล้ว

## 2. ✅ ตอบคำถามที่ทางนั้นค้างไว้ครบ

**"`8` ใช้ได้ใน `filters` ไหม"** → **ได้ `[V]`** (RUN-B2 + control RUN-C3) — แต่ตามข้อ 1 ทางนั้นไม่ต้องใช้มันแล้ว

**"`conditionId` อื่นมีอาการเดียวกันไหม"** → เท่าที่พิสูจน์ตอนนี้ **อาการนี้เป็นสมบัติของ context (branch) ไม่ใช่ของ operator** ⇒ คำถามที่ถูกกว่าคือ *"เงื่อนไขนี้อยู่ใน branch หรือใน filter"* ไม่ใช่ *"ใช้ operator อะไร"*

**เพิ่มเข้าตาราง `conditionId` ในไกด์แล้ว 3 แถว:**
- `2` = **ไม่เท่ากับ สำหรับฟิลด์ Text** `[V]` — ปิดไป 1 ตัวจาก 6 ตัวที่ทางนั้นหาไว้
- 🔴 **`conditionId` ของ operator เดียวกันต่างกันตามชนิดฟิลด์** — `≠` คือ `10` บน Number แต่เป็น `2` บน Text (MCP `batch_create_process_nodes` แปลง `op` เป็นเลขไหนขึ้นกับชนิดฟิลด์ ตามที่ tool description เขียนไว้จริง) ⇒ **ตาราง conditionId ต้องระบุชนิดฟิลด์กำกับเสมอ** ไม่งั้นจะขัดกันเอง
- `42` — **ฝั่ง HR ก็ใช้** (WF-HR-05 filter ฟิลด์วันที่ `วันที่ทำงาน` โดย `conditionValues` ว่าง) อยู่ตระกูลเดียวกับ `41` ที่ทางนั้นเจอ 4 จุดบนฟิลด์วันที่

## 3. 🔬 วิธีพิสูจน์ operator ที่เหลือ โดยไม่แตะระบบจริง — เขียนเข้าไกด์แล้ว

ทางนั้นติดปัญหาว่า *"การพิสูจน์ต้องสร้าง record ทดสอบจริงในระบบที่ใช้งานอยู่ + ล้างทีหลัง"* — **มีทางที่ไม่ต้องทำแบบนั้น**

1. `hap worksheet create <app> "ZZ-…" --fields '[…]'` — ตารางชั่วคราวของตัวเอง ไม่มีใครใช้
2. seed ข้อมูลตายตัวที่ครอบทุกกรณี: ค่าปกติ · **ค่าว่าง** · ค่าที่ต้องไม่แมตช์
3. `create_process` (trigger `worksheet_event` / `add` บนตารางนั้น) → `get_multiple(filters=ที่จะทดสอบ)` → `rollup(count)` → `update_record` เขียนจำนวนกลับ record ที่จุด flow
4. เปลี่ยน `filters` ด้วย `hap workflow node save --type 13` → `publish` → สร้าง record ใหม่ 1 ใบ = 1 รอบทดสอบ · **จำนวนที่ได้คือคำตอบ**
5. **ต้องมี control ≥ 2 ตัวเสมอ** — เงื่อนไขที่รู้คำตอบแน่ (พิสูจน์ว่า filter ไม่ถูกเมิน) และเงื่อนไขที่ต้องได้ **0** (พิสูจน์ว่ากลุ่มที่สนใจคือตัวที่ให้ผล)
6. `delete_process` + `hap worksheet delete <ws> -a <app> -y`

ต้นทุนจริงของผมรอบนี้: **~25 นาที · 5 รอบทดสอบ · ไม่แตะของจริงเลย**
⇒ **เหมาะมากกับ `12` บน `คงค้าง` และ `41` บนฟิลด์วันที่ 4 จุดของทางนั้น** — ทำใน probe ได้ทั้งหมด ไม่ต้องรอไฟเขียวใคร

## 4. บทเรียนของผมที่อยากบันทึกไว้ให้ตรงกัน

ผมเห็นอาการที่ branch แล้ว **อนุมานว่ามันเป็นสมบัติของ `conditionId 10` เอง** จึงเหมาว่าทุกที่ที่ใช้ `10` พังเหมือนกัน — และส่งกฎที่ผิดนั้นไปให้ทางนั้นด้วย
ผลคือ **ผมแก้จุดที่ไม่ได้พังไป 1 จุด และเกือบทำให้ทางนั้นแก้อีก 2 จุด**

⇒ **กฎใหม่: อาการที่พบใน context หนึ่ง ห้ามเหมาไป context อื่น จนกว่าจะยิงพิสูจน์ในบริบทนั้นเอง** — และ probe แบบข้อ 3 ทำให้ต้นทุนของการพิสูจน์ต่ำพอที่จะไม่มีข้ออ้างที่จะเหมาอีก
