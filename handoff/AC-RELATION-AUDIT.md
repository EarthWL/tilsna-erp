## 1. 🔴 วิธีตรวจที่เราใช้ทั้งคู่ **มองไม่เห็นบั๊กที่ผมเจอจากข้อมูลจริง**

ผมออดิตฝั่งบัญชีตามวิธีของทางนั้น — ไล่ `fieldValueId` ของทุก field write หาตัวที่เป็น nodeId

**ผลรอบแรก: 0 จุด** ทั้งที่ผมมีหลักฐานจากข้อมูลจริงว่า `AC_GL.voucher` มี sid เป็น nodeId อ่านกลับได้ `已删除`

**เพราะกลไกที่ทำให้พังไม่ใช่ `fieldValueId`** — ของจริงหน้าตาแบบนี้:

```
node 'สร้างรายการในบัญชีแยกประเภท' (inner ของ WF-AC-02)
  fieldId      6a85fb419b6999a714d2a58e   ← AC_GL.voucher (type 29 Relation)
  fieldValueId ''                          ← ว่าง
  fieldValue   '["6a8ea7b8730d20c5b7604a55"]'   ← nodeId ยัดเป็น literal ตรง ๆ
  nodeId       ''
```

⇒ สคริปต์ที่ดู `fieldValueId` จัดรายการนี้เป็น **"ว่าง = no-op ไม่เขียนค่าใด ๆ"** ทั้งที่มัน**เขียน** — เขียน literal ที่บังเอิญเป็น nodeId

> 🔴 **นี่คือรูปร่างที่สาม ซึ่งเกณฑ์ของเราทั้งคู่จับไม่ได้**
> **A** `fieldValueId` = nodeId (ที่เราตรวจกัน)
> **B** `kind:"record"` (ที่ WF-AC-10 เคยเจอ)
> **C** `fieldValueId=""` **+** `fieldValue` = literal ที่มี nodeId ← **ตัวนี้**
>
> ทางนั้นเขียนในตารางว่ามี "รายการว่าง (`fieldValueId=""`, `fieldValue=""`, `nodeId=""`) 1 จุด — no-op" · **ถ้าตอนนั้นเช็ค `fieldValue` ด้วยจริง ก็แปลว่าฝั่ง HR สะอาดจริง** แต่ถ้าเกณฑ์ที่ใช้คือ `fieldValueId` อย่างเดียว **ขอให้รันซ้ำด้วยเกณฑ์ C** เพราะรายการแบบนี้จะโผล่มาในกอง "no-op" เหมือนกัน

## 2. เกณฑ์ที่คมกว่า — แยกของจริงออกจากของหลอกได้

รอบสองผมกวาดหา nodeId ใน `fieldValue` ของทุก field write **ได้ 15 จุด — แต่ 14 จุดเป็นของถูกต้อง**

ของถูกคือ **template placeholder `$nodeId-fieldId$`** บนฟิลด์ Text (type 2) เช่น
`'REV-$6a8f49b8730d20c5b764f2ff-6a85ff5933560633b8cd9f83$-$…-utime$'` — เป็นวิธีที่ถูกต้องในการแทรกค่า

**ตัวเดียวที่ผิดคือตัวที่ไม่มี `$…$` ครอบ** ⇒ ลายเซ็นที่แม่นคือ:

> **ปลายทาง type 29 (Relation) + `fieldValueId` ว่าง + `fieldValue` เป็น literal ที่ไม่มี `$…$`**
> ⇒ ค่าที่ถูกเขียนคือสตริงดิบ ไม่ใช่การอ้างอิง ⇒ ถ้าสตริงนั้นเป็น nodeId จะได้ `已删除`

```python
bad = (f.get('type')==29
       and not (f.get('fieldValueId') or '').strip()
       and str(f.get('fieldValue') or '').strip()
       and '$' not in str(f.get('fieldValue')))
```

## 4. ผลกระทบจริงของบั๊กนี้

`AC_GL.voucher` เชื่อมกลับไปใบสำคัญไม่ได้ทุกแถว ⇒ **รายงานหรือ rollup ใดที่วิ่งผ่าน relation นี้จะได้ค่าว่าง** (เช่น การไล่จากใบสำคัญไปหารายการ GL ของมัน)
ยังตามรอยได้เพราะ node เดียวกันเขียน `voucher_row_id` (Text) ถูกต้อง — **แต่นั่นคือ workaround ไม่ใช่ของที่ควรเป็น**

**ยังไม่แก้** — เป็นการเขียน workflow ที่ใช้งานจริง และ **การแก้ workflow อย่างเดียวไม่พอ**: GL 5 แถวที่มีอยู่จะยังเสียอยู่ ต้องตัดสินใจพร้อมกันว่าจะลบแล้วผ่านรายการใหม่ หรือแก้ relation ทีละแถว
วิธีแก้ที่ถูกตามกฎที่ทางนั้นเขียนเข้าไกด์ §2 ข้อ 19: เปลี่ยนเป็น **`fieldValueId: "rowid"` ชี้ node `ดึงใบสำคัญแม่`** (แบบ ก)
