## 2. 🔴 ของที่อยากให้ทางนั้นรู้ที่สุด — **ผมเขียนออดิตไว้ผิด**

ใน `AC-RELATION-AUDIT.md` ผมสรุปว่ารูปแบบที่ถูกของ relation คือ `fieldValueId: "rowid"` · ผมจึงเตรียมแพตช์เป็นแบบนั้น

**แต่พอแก้ผ่านหน้าจอ Nocoly จริงแล้วอ่านค่ากลับ ได้แบบนี้แทน:**

```
fieldId      6a85fb419b6999a714d2a58e   (ac_gl.voucher · type 29)
nodeId       6a8ea7b8730d20c5b7604a55   ← node 'ดึงใบสำคัญแม่'
fieldValueId ''                          ← ว่าง ไม่ใช่ "rowid"
fieldValue   ''
```

⇒ **relation-to-record มี 2 รูปแบบที่ถูก:**

| | หน้าตา | ที่มา |
|---|---|---|
| **ก.** | `fieldValueId: "rowid"` + `nodeId` | ที่เราเขียนเข้าไกด์ (พบใน WF-AC-10 `newVoucher`) |
| **ข.** | **`nodeId` + `fieldValueId` ว่าง** | **สิ่งที่ UI ของแพลตฟอร์มเขียนออกมาเอง** ⇒ canonical |

🔴 **ผลกับทางนั้นโดยตรง:** ถ้าสคริปต์ออดิตฝั่ง HR ใช้เกณฑ์ `fieldValueId == "rowid"` อย่างเดียว **มันจะฟ้องรูปแบบ ข. ว่าผิดทั้งที่ถูก** — และรูปแบบ ข. คือสิ่งที่จะเกิดขึ้นกับ **ทุก node ที่คนแก้ผ่านหน้าจอ** · ขอให้รันซ้ำด้วยเกณฑ์ที่ยอมรับทั้งสองแบบ
บันทึกเป็น **D-23** ใน `MIGRATION.md` แล้ว

> บทเรียนของผมรอบนี้ต่อจากรอบ refcheck: รอบก่อนผมเชื่อตัวตรวจที่คิดแบบเดียวกับตัวแก้ · รอบนี้ผม**เกือบ**เขียนกฎจากตัวอย่างเดียวที่บังเอิญเจอ · **ตัวอย่างเดียวไม่พอจะประกาศเป็นกฎ**

## 4. 🔴 ของใหม่ที่ยังไม่แก้ — `gl_no` ไม่สมบูรณ์ (รอผู้ใช้กำหนดรูปแบบ)

`ac_gl.gl_no` (`เลขที่รายการบัญชี` `6a860c4d1049edca1eed02d6`) เป็น **AutoNumber** ที่ออกมาเป็น `27GL-` `28GL-` … **ลงท้ายด้วยขีดแล้วไม่มีอะไรต่อ**

- **ไม่ใช่บั๊กของ workflow** — workflow ไม่แตะฟิลด์นี้เลย เป็นรูปแบบเลขอัตโนมัติระดับตาราง
- **สเปกไม่เคยนิยามว่า `gl_no` ควรมีหน้าตาอย่างไร** (NFR-05 พูดถึงแค่ `movement_seq`) ⇒ **ผมไม่เดารูปแบบเลขเอกสารบัญชีเอง** ส่งให้ผู้ใช้ตัดสิน
- อ่านรูปแบบผ่าน API ไม่ได้ — `hap worksheet fields` **ไม่คืน `advancedSetting` ของ AutoNumber** ⇒ ต้องเปิดใน Browser · บันทึกเป็น **D-22**

**ถ้าฝั่ง HR มีฟิลด์ AutoNumber ที่ตั้งรูปแบบไว้ ลองเช็คว่าโดนอาการเดียวกันไหม** — อาการนี้มองไม่เห็นจาก API เลย เห็นได้จากค่าที่ออกมาเท่านั้น
