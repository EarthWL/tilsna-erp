## 🔴 อ่านข้อนี้ก่อน — กระทบวิธีทำงานของทั้งสองฝั่ง

### `get_workflow_structure` อ่านเงื่อนไขซ้อนกลุ่มออกมา **แบน**

`A AND (B OR C)` ถูกอ่านกลับมาเป็น `and` สามเงื่อนไขเรียงกัน — **หน้าตาเหมือน `A AND B AND C` เป๊ะ ๆ**

**พิสูจน์แล้วด้วยการทดลอง** (สร้าง workflow ชั่วคราวแล้วลบทิ้ง):
1. เขียน branch `A AND (B OR C)` ผ่าน `batch_create_process_nodes`
2. อ่านกลับด้วย `get_workflow_structure` → กลุ่ม OR หายไป เหลือ `and` สามข้อ
3. publish แล้วยิงจริงด้วยข้อมูลที่ **B จริง / C เท็จ** → **ลงสาขา A** (เขียนค่า `PROBE-OR-KEPT`)

⇒ **ของถูกเก็บและทำงานถูก แค่ "อ่าน" ออกมาผิด**

**สิ่งที่ทางนั้นควรทำ**
- ✅ **สบายใจได้**: ทางแก้ D-19 (กระจาย AND ทับ OR) ที่เขียนผ่าน MCP ถูกเก็บจริงและทำงานจริง
- 🔴 **ห้าม** ใช้ `get_workflow_structure` ไล่ตรวจว่าทางแก้ D-19 ยังอยู่ครบไหม — จะอ่านได้ว่า gate "ไม่มีทางเป็นจริง" ทั้งที่ยิงอยู่ทุกวัน · **ถ้าไป "แก้" ตามที่อ่าน จะทำของดีให้พังจริง**
- ถ้าต้องตรวจตรรกะ branch จริง ๆ: เปิดดูใน Browser หรือทดสอบด้วยข้อมูลจริงแบบที่ทำข้างบน

## 1. ผลไล่ตรวจ workflow บัญชีที่ publish แล้วทั้ง 8 ตัว (ตาม D-33 / D-34)

เจอของจริง **1 จุด** — **WF-AC-01 เขียน `reject_reason` สองที่ (`rej_unbal`, `rej_period`) แต่ไม่มี node ไหนล้างเลย**
⇒ ใบที่ถูกตีกลับ แก้จนถูก ส่งใหม่ผ่านแล้ว **ยังค้างข้อความตีกลับของรอบก่อน**

**แก้แล้ว publish v3** — ให้ node `set_flag` (ซึ่งวิ่งทุกครั้งที่เริ่มรอบส่งอนุมัติใหม่) ล้างให้ · ทดสอบครบทั้งสองทาง

> **ฝั่ง HR ควรไล่ข้อเดียวกัน** — workflow ที่มีเส้นทางตีกลับ/แจ้งเหตุผล (ใบลา ใบ OT ใบขออัตรากำลัง) น่าจะมีอาการเดียวกัน · อาการนี้ **ไม่มีทางเจอจากการใช้งานปกติ** เพราะระบบทำงานถูกทุกอย่าง แค่ข้อความค้าง

**อีกข้อที่ควรรู้:** WF-AC-11 มี `get_multiple` ที่ค้นตารางเดียวกับ trigger และ **นับตัวเองด้วย** — แต่ **ถูกต้องตามความหมาย** (จะปิดปีได้ ทุกงวดรวมงวดที่กดต้องปิดก่อน)
⇒ 🔑 **D-33 ไม่ใช่กฎอัตโนมัติ** ต้องถามทุกครั้งว่า "แถวของตัวเองควรถูกนับไหม" ไม่ใช่ใส่ `rowid ne` ทุกที่

## 3. WF-AC-24 v3 — ปิด R6 และ R7

- **R6** `submitted_flag` ไม่เคยถูกตั้งเป็น 1 ⇒ ให้ node `pass_ok` บนสายที่ผ่านด่านตั้งให้
- **R7** เหตุผลกำกับเอกสารซ้ำเคยใช้ได้ตลอดไปแม้ผู้ใช้แก้เลขที่ใบไปชนใบอื่น
  ⇒ แก้โดย **ผูกเหตุผลกับคีย์** ไม่ใช่ล้างฟิลด์ทิ้ง: code node เทียบ `dup_key` ที่ระบบตรวจไว้ล่าสุดกับคีย์ปัจจุบัน ถ้าไม่ตรง = เหตุผลหมดอายุ
  🔑 **ดีกว่าการล้างฟิลด์ เพราะไม่ทำลายสิ่งที่ผู้ใช้พิมพ์ แค่บังคับให้ทบทวน**
  🔴 ต้อง **ย้ายการเขียน `dup_key` ออกจากหัวสาย** ก่อน ไม่งั้นค่าเดิมถูกทับไปแล้วตั้งแต่ยังไม่ได้เทียบ

ทดสอบครบ 6 เคส (TC-09 / 09b / 09c / 09d / 09e / 09f) ผ่านทั้งหมดด้วยข้อมูลจริง
